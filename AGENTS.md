# Agent rules

Read this file (including "Global design principles" and "Lessons from the audits" at the end), then `ARCHITECTURE.md` (where things live), then `HANDOVER.md` (what was built and how it is wired).

## Working rules (from the owner)

0. **Unified designs only; never hard-code.** Every control, style, layout piece, list and rule uses the existing shared (master) piece. If none fits, create ONE shared piece and use it everywhere it applies, then document it in "Master design elements". Hard-coding a look, size, text, list or behaviour into one place is allowed only when truly unavoidable, and then the reason is written in `HANDOVER.md`. Never add pages, sections or features that were not asked for, and never build a new or changed design the owner has not approved (show a visual first).

1. **No visuals** (mockups, diagrams, widgets, screenshots) unless the owner explicitly asks. When asked, show the visual first and build only after approval.
2. **Finish = build, stop, relaunch** (but only after the whole job queue has finished, see "How jobs are run"). When work is finished, build, stop any running `OmniControl.exe`, and launch the app for the owner. Stop the app before building or the build fails with locked files.
3. **One feature at a time**, scalable: a new page is a view-model, a view, one line in `ShellViewModel`, and one DataTemplate in `App.axaml`.
4. **Every feature registers bindable hotkeys** (`HotkeyRegistry.Register(new HotkeyAction(...))`), e.g. brightness up/down. They appear automatically as searchable cards in Shortcuts. For variable devices (monitors, speakers...) pass a device source so the user can pick all or a subset.
5. **Keyboard and mouse both work everywhere**, with one owner-set exception: pop-up and pop-down menus opened from a control (the Volume Plays on menu on both tabs, the Method menu, option cards and similar submenus) are designed like a proper program's menus, mouse first, compact and clean; they do not have to be keyboard-navigable inside (Esc to close and the control that opens them staying keyboard reachable is enough). Never trade their looks for keyboard support. The same applies, at the agent's judgement, to anything where a mouse-optimised design is clearly the better one (drag and drop, rubber-band selection, graphs and curves, colour or file pickers, popovers, dialogs): design it for the mouse first, keep the control that opens it reachable and operable by keyboard at a basic level, and note the choice in `HANDOVER.md` so the owner can overrule it. Keyboard focus shows the accent colour (no default white outline); every clickable item has a hover effect (styles in `Styles/Theme.axaml`). Up/Down wraps at both ends (sidebar and page lists).
6. **Never overlap or clip.** No fixed-width text columns: use `Width="Auto"` with a `SharedSizeGroup` inside `Grid.IsSharedSizeScope`, and give text that can grow `TextWrapping="Wrap"` or `TextTrimming`. **Fit text in the space the card already has**: do not make a card taller or wider to hold a long label. Prefer, in this order: wrap to two lines at the same card height (`TextBlock.cardlabel` in `Theme.axaml` does this for compact one-line cards), then shorten the wording, then trim with an ellipsis as a last resort. Before finishing a UI change check the longest label, the narrowest window (minimum width in `MainWindow.axaml`), the search-results view, and both themes.
7. **Do not use the PC to test.** No simulated key presses or mouse input, no window automation, no changing system state (brightness, volume, registry, other apps). Reason from code and a clean build; the owner tests. (Past automated tests changed the owner's real settings.) Say what was and was not checked.
8. **Keep concerns separate.** Dependencies point down only: Core never references App, services never reference pages, pages never reference each other. A view-model never calls Win32/COM directly; views hold layout only. One concern per file, no file over 700 lines (split by concern; a `partial` class is fine). Keep `ARCHITECTURE.md` current.
9. **No hard-coding.** Intervals and grace periods live in `App/Services/Timing.cs`; colours come from theme resources and `AccentService`, never literals in views; persisted values live in the settings classes.
10. **Tidy as you go.** Remove dead code, stale notes and unused files when you touch an area; do not leave TODO notes in code (put open items in `HANDOVER.md`).

## Conventions the owner has set

- Orange accent by default, soft/hover tints kept transparent (`AccentService`); the theme and accent choice are Left/Right gallery cards, not drop-downs.
- Cards: label left, control right; keyboard Up/Down moves between cards, Left/Right edits or walks parts of a row, Enter activates. Half-width cards (`Half = true` on a `ToggleItem`) pair two per row and Up/Down follows reading order.
- Honest reporting: the effects engine (`App/Audio/Engine`) says on every row and FX window what really happens (running with its delay, waiting, not installed, failed and why; `EngineStatus`). Never imply processing that is not happening: effects an engine does not run (`FxKind.Engines`) are stored only and the UI says so; VST3 plug-ins on Equalizer APO rows are kept but not run there; a VST2 plug-in that Equalizer APO runs is said to run with the settings saved in OmniControl (its defaults until any are saved) and with an unknown delay; plug-ins that won't load (32-bit, an instrument, not a plug-in) are refused with a one-sentence reason (`PluginLoader`); for the master in Equalizer APO OmniControl can only say the chain was sent, not that Windows applied it.
- Windows icon cache may show the old icon until Explorer restarts.

## Code quality rules

11. **Understand before you change.** Read the files around your change, and the nearest existing example of the same kind of thing (another page, card, service or hotkey), before writing anything. Copy that pattern; do not invent a second way to do something the code already does. If the existing way is wrong, say so and fix it everywhere, or leave it. No one-off exceptions.
12. **Keep code pieces loosely coupled.** A piece of code should know as little as possible about the others. Call another class only when your job truly needs its result.
    - Ask "who owns this?" before each call. If another class owns the data or rule, ask that class. Do not reach into its internals, duplicate its logic, or copy its state.
    - No chaining through objects (`a.B.C.D`), and no reading another class's private details through casts, reflection or shared statics.
    - Prefer a small interface, a callback (`Action`) or an event over a direct reference to a concrete class (as `MixerItem` reports changes).
    - No circular references. If two classes need each other, one is doing the other's job: move the shared piece to a third place.
    - No global mutable state. A static is fine for constants and pure helpers only.
    - Each method does one thing; a class has one reason to change.
13. **Put each piece of logic in one place.** No copy-paste: if the same logic appears twice, move it to one helper. Rules, limits and defaults are defined once and referenced; never retype a number or string. Views do not make decisions: the view-model decides, the service acts, Core talks to Windows (rule 8).
14. **Keep the design consistent.** Before adding anything, say in one sentence which layer it belongs to and why; if it does not fit cleanly, the design needs thought, not a workaround. Use the same word for the same idea everywhere. Prefer the simplest change that fits the existing design: no new abstraction, layer or dependency unless it removes real duplication or coupling today, and no features nobody asked for. Make things `private` or `internal` by default.
15. **Write safe, readable code.** No empty `catch` that hides failures: catch the specific exception, handle or log it, and comment why when not obvious (Windows calls can fail; keep the app running). Release what you acquire (COM objects, handles, timers, event subscriptions). UI work stays on the UI thread; slow work stays off it. Leave no commented-out code, dead code, unused parameters or debug output. Comments explain why, not what.
16. **Check your own work.** Before building, re-read your diff against these rules (coupling, duplication, hard-coding, wrong layer). Leave an area tidier than you found it within the current task; report bigger problems as open items in `HANDOVER.md` rather than fixing them silently. Update `ARCHITECTURE.md` and `HANDOVER.md` when files move or behaviour changes.

## Global design principles (owner's, apply to the whole program)

These came from comments on single screens but are rules for **every** control and page, present and future. Implement each one **once**, in a shared place (a style in `Styles/Theme.axaml`, a shared row template, an attached property or a class handler registered at start-up), and let every control pick it up from there. Never hard-wire a behaviour, colour, size or text into one individual button, card or action, and never copy it per control: if a control does not behave like the others, fix the shared piece, not the control.

1. **Hover and focus** come from the master styles (`Theme.axaml`); no control hard-codes its own hover, and hover never moves or resizes text (no border-thickness changes).
2. **Values change live.** Changing a setting takes effect at once; there is no Apply step. Only choosing a different action (a new pick) needs a confirm ("Use this action").
3. **Every value control can be driven four ways:** mouse (click or drag), keyboard (Left/Right or Up/Down), the **mouse wheel while hovering it** (`ValueWheel` for sliders and drop-downs, the option window for numbers and choices), and, for numbers, **typing**: double-click or Ctrl+Enter opens a box; clicking away, moving focus or Tab applies the typed value (same as the value being accepted), Esc cancels. Enter applies and confirms, it never starts typing.
4. **Double-click a slider to reset it** to its default (`SliderReset`; the default is stated where the slider is defined: pan 0, volume 100...). **Knobs (owner's explicit rule):** a single left click without a drag opens the value for typing, a double-click resets, a drag up or down turns it; so on a knob typing needs no double-click (the `Controls/Knob` master and `NumberText.Register` do this once for every knob).
5. **Settings that several items share** (the same gesture action on many areas) are edited once and applied to all by a switch that is **on by default**; turning it off edits one item only.
6. **Steps mean real amounts.** "Change per wheel notch" is the actual change (default 5 %), never a repeat count hidden behind another name.
7. **Placement:** labels on the left, the control itself (drop-down, gallery, colour dots) **centred in its card**; colour dots and gallery items are directly clickable as well as steppable.
8. **Compact density:** one base text size (`ControlContentThemeFontSize` in `App.axaml`), tight padding from the shared styles, no dead space inside cards, text wraps to a second line before the card grows.
9. **Feedback near where it is wanted:** state that belongs to one page (the active mouse layer) is shown only on that page.
10. **Safety:** anything that launches programs or sends keys on its own must be rate limited and must always release what it presses.
11. **Calm wording:** warnings are short, factual and in proportion: one plain sentence, the detail in a tooltip, the docs or a log, never a list of scary scenarios in a dialog. Red only for a real failure, yellow sparingly, one tag per fact that matters. An unexpected error shows one plain sentence with the next step, "Copy details" and the log path, never a raw exception.

12. **No keyboard instructions on screen.** Never write paragraphs or footer strips of keyboard instructions at the bottom of pages or windows (no "Up/Down move between rows; Left/Right choose a part…" text). Keyboard operation still has to work (rules 5 and 3), but it is learned from tooltips, a single "Keyboard shortcuts" item in a window's menu or the app's help, and from the controls behaving as expected, never from reserved screen space. A short factual status line is allowed only when it carries real state (such as the effects engine's status) and then it is one thin line in a small font.
13. **Fit more, clutter less.** Every page and window should show many options without crowding: think about the layout before adding anything. Prefer the space-saving form that is still easy to see and reach: half-width cards where two fit side by side instead of full-width cards, one toolbar row instead of several stacked rows, a control placed beside what it affects instead of under it, smaller (but still readable) type for secondary values, tooltips for explanations, and the saved space given to the thing the user is working on (an editor, a graph, a list). Group related controls, align them on shared columns, and keep the most used controls the most visible. Check each change at the narrowest window and say what you did to keep it uncluttered.
14. **One design language across the whole program (owner's rule).** The same kind of thing is designed the same way and sits in the same place everywhere. Before adding or changing anything, find how the program already does that kind of thing and do it identically: if presets for a group are the master preset picker (`Controls/PresetPicker`: a drop-down whose list ends with a thin line and "Manage presets…", which opens the preset manager at that group) on the group's header line (Mouse Buttons, Trackpad), then presets for any other group (Displays Hardware and Software, the Volume page's presets at the right of its tab row, a future group) are the same picker on that group's header line, with no separate cogwheel, not a card, a button or a separate window entry; a section's 'Restore defaults' is the pill at the right of its title line; a state or fact is a `Border.tag`; a choice among a few is the shared pop-down card list. If a new case does not fit the existing pattern, extend the pattern in the shared piece and update every user of it, never invent a second way for one page. When you touch a page, check its siblings for the same inconsistency and fix or report it in `HANDOVER.md`.

## Lessons from the audits (check before you write; the same mistakes were found again and again)

- **Pop-downs sit in the logical tree under the control they open from,** so a descendant selector on a page style (`ListBox.rows ListBoxItem`, `Button.link TextBlock`) reaches into them. Style a container's own items or content with the child selector (`ListBox.rows > ListBoxItem`, `Button.link > TextBlock`), and size glyphs in a context after the generic `Path.glyph` (no specificity in Avalonia: the later style wins).
- **Look for the shared piece first.** It probably exists: every saved json file is an entry of `Services/DataStore.cs` (`DataStores`; `AppDataStore` takes only entries, backup and wipe read the list); colours `Services/Palette.cs` and `Styles/Theme.axaml`; percent maths `Core/Models/Percent.cs`; App timings `Services/Timing.cs`, Core timings `Core/CoreTiming.cs`; wrap-around and Up/Down `Services/Wrap.cs`; "ignore the echo of my own change" `Services/Grace.cs`; search matching `Services/TextMatch.cs`; wheel, double-click reset and number typing `Pages/ValueWheel.cs`, `Pages/SliderReset.cs`, `Pages/NumberText.cs`. Never retype a number, colour, key name or rule that has a home; if it has none, give it one and use it from there.
- **No per-control behaviour.** Do not add a wheel, reset, typing, hover or focus handler to one control; register or style it once so all controls get it.
- **Layers:** no Win32, COM, WMI or registry in `App` (it belongs in `Core/Engine`); no page imports another page (shared pieces go to a neutral place); views hold layout and wiring only, key routing and decisions belong in the view-model.
- **No new static mutable state;** unsubscribe from events you subscribe to and dispose what you create; catch the specific exception, never a bare catch.
- **Lean means deleting:** after a change remove what it made unused (grep before deleting; source-generator and XAML-bound members look unused but are not); no commented-out code, no notes in code (open items go in `HANDOVER.md`).
- **Refactors keep looks and behaviour identical;** say what you could not keep. Build after each step and stop the app first (fresh output folder per build: `bin\Relaunch<HHMMSS>`).
- **Scripted multi-file edits need checking:** after a sed or perl edit, grep or diff the result; prefer the Edit tool for anything with quotes, pipes or newlines.
- **Bindings are resolved at run time here** (compiled bindings are not enabled, so `x:DataType` only documents): a type prefix inside a binding (`$parent[fx:MyControl]`, `((vm:MyModel)DataContext)`) cannot be resolved and crashes the window that contains it, only when it opens. Never put a namespace prefix inside a binding path: use `$parent[UserControl]`, a plain property path, or put the command/property on the item view-model. Before finishing, grep every `.axaml` you touched for `\$parent\[[a-z]+:` and `\([a-z]+:[A-Za-z]+\)`.
- **Do only what was asked.** Never add a page, sidebar section, setting or screen the owner did not request (an unrequested "Apps" page was built and removed); if something seems missing, report it instead.
- **Docs travel with code:** every new file gets its line in `ARCHITECTURE.md`; a changed behaviour is corrected in `HANDOVER.md` in the same task.
- **Subagents:** whoever spawns one starts its prompt with "Read AGENTS.md first and obey it"; an agent that reports done lists what it skipped and what is unverified.

## How jobs are run (owner's default for every session)

- **One job at a time.** Never run several agents or jobs in parallel unless the user asks for that specifically. Queue them and start the next only when the previous one has finished and reported; a job that must wait for others (such as a layout change after other work) waits until all agents are done.
- **Default agent: Sonnet at LOW effort** for every job from 13 Nov 2026 on (the owner changed it from medium; the jobs before that were run on Opus medium on purpose). Use a different model or effort only when the user sets another default for that session, or asks for a specific agent for that specific job. Read-only mapping scans may still be given to a cheaper agent when the user asks for one.
- Every agent prompt starts with "Read AGENTS.md first and obey it" (see "Lessons from the audits").
- **Stay autonomous; never run dry.** The queue of owner-approved jobs is kept in the session's task list and in `HANDOVER.md`. The moment a job reports, the next queued job starts without waiting for the owner; the turn ends only when the queue is empty, a real decision needs the owner (a question, an approval for something outward-facing such as a push), or the owner stops the work. Before ending a turn, check that no approved job is left unstarted and that no agent has finished with nothing started after it. Anything the owner asks for mid-work is added to the queue at once, in order, and acknowledged.
- **Orchestrator review on every new request** (the orchestrator is the agent talking to the owner). Whenever the owner adds a feature to the queue, the orchestrator first reviews the running job(s) and every queued job and decides, before starting or queuing anything: (1) does the new request overlap, contradict or make part of an existing job unnecessary (then change the job's brief, or message the running agent, so work is not duplicated or scrapped later); (2) does it touch the same files or the same subject as a running or queued job (then give it to the same agent if that agent's context is still small, or queue it directly after, never in parallel on the same files); (3) can related jobs be combined into one brief so one agent does them together, with the shared design known once; (4) is an agent's context getting large (a long job, many follow-ups, many files read): then do not pile more onto it; start a fresh agent with a complete brief instead. Re-order the queue when that avoids rework (for example a shared piece first, its users after). The orchestrator states the outcome in one or two lines to the owner (what moved, what was merged, which agent got what) and keeps the queue in the task list current.
- **Approved mock-ups travel as files.** Whenever the orchestrator shows the owner a mock-up (a visual) and the owner approves it, the orchestrator saves the approved version as a real file (HTML, with its sizes and a comment saying what each part is) in `docs/mockups/<short-name>.html` BEFORE starting the job, and puts its path in the agent's brief. A description in words is never enough. The agent opens that file, builds to match it as closely as the master styles allow, and its report lists every place where the result differs from the mock-up and why. If the owner changes the design afterwards, the file is updated to the new approved version first. Mock-ups of rejected options are not saved.
- **No app rebuild or relaunch until the whole queue has finished** (this overrides "Finish = build, stop, relaunch" for each single job). Agents on a queued job check that their code compiles with a build into a throwaway folder (`bin\chk<HHMMSS>`, deleted afterwards) but do not stop the running app and do not launch a new one; the one real build and relaunch happens after the last job reports. Exception: the user asks for a rebuild or relaunch before then.

## One master list (owner's rule: nothing is listed by hand in more than one place)

Everything the app can do, and everything it can be searched for or shown as, comes from ONE master list per kind, and every consumer reads that list; nothing that consumes it keeps its own hard-coded copy. Adding a new action, setting, device, gesture area or OSD element must be a single registration in one place and it then appears automatically everywhere it applies (the Shortcuts page, the mouse button and gesture action pickers, search results, OSD elements, hints, keywords...). If you find a second hand-written list of the same things, replace it with the master list. Never ask an agent to "also add it to X": if that is ever needed, the design is wrong and must be fixed first. Where a list needs extra data (a category, a group such as Hardware or Software, a device scope), that data lives on the master entry. See `ARCHITECTURE.md` for where each master list lives.

Learned in the master-list audit (keep these when you touch a list):

- **Read the live list, never a copy taken once.** A page that copies the registry when it is built misses everything registered later (three actions were missing from the mouse and gesture pickers this way). Consumers subscribe or rebuild when the list changes, so registration order never matters.
- **What is decided by matching text belongs on the entry.** An icon or look picked from the first word of a label, or a category typed as a string, is a hidden second list: make it a field on the entry (`OsdElement`, `HotkeyAction.Group`) and take categories from the owning page's `Title`.
- **No second copy of an action, and no side lists of ids.** Do not add a built-in action that an OmniControl action already covers; a list of ids that repeats a catalogue's own table (repeatable, window action, mode) is a flag on each entry instead.

Automation (owner-approved, see `ARCHITECTURE.md`): a Do rule's hotkey is the shortcut of the rule's own master action, never stored on the rule; every action a user or a rule makes (custom action, "Run: rule", power action) is registered once in `HotkeyRegistry` and appears everywhere. Block rules are enforced at the ONE gate in `HotkeyRegistry` (`IActionGate`), so an action that must never be blockable is flagged `HotkeyAction.NeverBlock` on its entry (no side list), and keys that no action may have are in `Hotkeys/ReservedKeys.cs`. Power calls live in `Core/Engine/PowerCommands.cs`; the countdown and start-up grace for sleep, shut down and the like are `Automation/PowerGuard.cs` (values in `Timing.cs`). The sentence parts (`Pages/SentenceBlocks.cs`) and their keyboard focus (`Pages/SentenceFocus.cs`) are shared by the gesture rule editor and the Automation rows.

- A button that needs a look no master gives is a gap in the master: add a class to `Theme.axaml` once (or extend one), document it here, and use it everywhere it fits. Placement goes in the view; look goes in the style.
- Agents never invent a button design. Before writing `<Button>`, read the master list above and `Theme.axaml`; a `<Button>` with no master class, or with local `Background`, `BorderBrush`, `CornerRadius`, `Padding` or `FontSize`, is a defect.

## Master list additions (audit-unify, no-look pass)

`ListBox.cards` (with `rows compact`) = the card list (pairs half-width cards; never write `ItemsPanel HalfPanel` by hand). `Border.sidebarpanel` = a window's side panel, `Border.barstrip` = a window's top bar (sidebar tint and divider edge; the control sets only which side its `BorderThickness` shows), `Border.pane` (+ `.edged` for the divider outline) = a boxed pane. `CrossIcon` (`Brushes.axaml`) = every drawn remove cross. `TextBlock.navheading` (`Theme.axaml`) = a sidebar group heading (small muted capitals; made by `Controls/NavList` from a `NavHeading`, never clickable, focusable or hovered; a page names its group in `PageViewModel.NavGroup`, texts in `Pages/NavGroups.cs`). Tags in code are `TagItem` (`Services/TagItem.cs`), drawn by `Controls/TagView`. Windows that exist once use `Services/SingleWindow<T>`. Asking or confirming goes through `Dialogs/DialogService.AskAsync` with a `DialogMessage` (`Confirm.Delete(kind, name)` for deletes). "Choose a program" is `PathPicker.PickProgramAsync`.
