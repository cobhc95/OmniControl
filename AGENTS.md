# Agent rules

Read this first, then `MAP.md` — the only place that answers "which piece, where, how do I add it" (layers, feature modules, master lists, folders, master UI pieces, recipes) and holds allowed exceptions and open items. `CHANGELOG.md` lists what changed.

## Design and code (owner)

0. **One shared design; never hard-code.** Every control, style, layout piece, list and rule uses the master piece in `MAP.md`. If none fits, make ONE shared piece, use it everywhere it applies, give it a `MAP.md` line. A one-place look, size, text, list or behaviour only when truly unavoidable, reason in `MAP.md` "Exceptions". Never build a design the owner has not approved.
1. **No visuals unless asked** (mock-ups, diagrams, widgets, screenshots); then show first, build only after approval (see "Mock-up discipline"). Approved mock-ups live at `docs/mockups/<short-name>.html` (sizes, a comment per part) only while the job is open, are named in the brief, updated before a design changes, and deleted once accepted; rejected options are never saved.
2. **Finish = build, kill, launch Setup** — once, after the whole queue (see "Versions, builds and releases"). Always launch the Setup installer, never the built `OmniControl.exe` from its `bin` folder.
3. **One feature at a time, as a module:** an `IFeatureModule` in `Features/<Feature>/` (services, actions, states, reloads, shut-down steps, pages; view templates through `ViewTemplate.For`, never `App.axaml`) plus its entry in the shell's module lists. Recipes in `MAP.md`.
4. **Every feature registers bindable actions** in the master list (`HotkeyAction`); they appear by themselves in the Actions and Hotkeys window, pickers and search. Variable devices (monitors, speakers…) get a device source so the user picks all or some. Every page declares its search words on its registration, from the same `SearchCard`/`SearchBuilder` definitions and the owning service's live data (menus, choices, tooltips count; never a hand-copied list), so search finds it without making the page; a new page or card is not done until search finds it (`PageSearchWordsTests` checks every page).
5. **Keyboard and mouse both work everywhere.** Exception: control-opened menus/pop-downs (Plays on, Method, option cards…) are mouse-first like a proper program's — compact, clean, Esc closes, the opening control stays keyboard reachable; never trade their looks for keyboard support. Same at the agent's judgement where mouse is clearly better (drag and drop, rubber band, graphs/curves, colour/file pickers, popovers, dialogs); note each in `MAP.md` "Exceptions". Focus shows the accent (no white outline), every clickable item has a master-style hover, Up/Down wraps at both ends.
6. **Never overlap or clip.** No fixed-width text columns (`Width="Auto"` + `SharedSizeGroup` in a `Grid.IsSharedSizeScope`); growing text wraps or trims. Fit text in the card's space, never grow a card for a label: wrap to two lines (`TextBlock.cardlabel`), then shorten, then trim. Check the longest label, the narrowest window (`MinWidth` in `MainWindow.axaml`), search results, both themes.
7. **Do not use the PC to test.** No simulated input, window automation or system-state changes (brightness, volume, registry, other apps) — past tests changed the owner's real settings. Reason from code and a compile; the owner tests. Say what was and was not checked.
8. **Layers and size.** Dependencies point down only: Core never references App, services never pages, pages never each other; no Win32/COM/WMI/registry in App (that is `Core/Engine`); a view-model never calls Windows; views hold layout and wiring only, key routing and decisions live in the view-model. One concern per file, none over 700 lines (split by concern; `partial` is fine); past ~1,000 lines over partials or 8 constructor parameters, move a concern into its own service.
9. **Every value has one home.** App timings in the feature's `Timing.<Feature>.cs` (partials of `Timing`; shared in `Shared/Services/Timing.cs`), Core timings in `Core/CoreTiming.cs`; colours from theme resources and `AccentService`, never literals; persisted values in settings classes, reached through setting slots (`ISettingSlot<T>`) or the feature's own `DataStore`, never `AppSettings.Current`. Never retype a number, colour, key name or rule that has a home.
10. **Tidy as you go, same task.** Remove dead code, stale notes, unused files where you work and what your change made unused (grep first: source-generated and XAML-bound members look unused but are not). No TODOs, notes, commented-out code or debug output in code; open items go in `MAP.md`.
11. **Understand before you change.** Read the files around the change and the nearest existing example of the same kind (page, card, service, action); copy its pattern, never invent a second way. If the existing way is wrong, fix it everywhere or leave it.
12. **Loose coupling, one home per logic.** Ask "who owns this?" before each call (and ask the owner); no reaching into internals, copied state/logic, `a.B.C.D` chains, or private details via casts, reflection or shared statics. Prefer a small interface, callback or event over a concrete class. No circular references (move the shared piece to a third place); no global mutable state (statics only for constants and pure helpers). One job per method, one reason to change per class; the same logic twice moves into one helper; rules, limits and defaults are defined once and referenced.
13. **Only what was asked; simplest fit.** Before adding anything, say in one sentence which layer it belongs to and why; if it does not fit cleanly, the design needs thought, not a workaround. Same word and one name per idea (never reuse a master control's class name); no new abstraction, layer or dependency unless it removes real duplication or coupling today; `private`/`internal` by default. Never add a page, section, setting or feature the owner did not request; report what seems missing.
14. **Safe, readable code.** No empty or bare `catch` (Core too): name the exception types, handle or log them, so a bug never looks like "no device". Release what you acquire (COM objects, handles, timers, subscriptions). UI work on the UI thread, slow work off it. Comments say why (and which Windows quirk), in one line — never what, history, dates, owners or mock-up paths.
15. **Check your own work.** Re-read your diff against these rules before compiling; compile after each step. Refactors keep looks and behaviour identical (say what could not be kept). Docs travel with code, same task: new folder/master piece/recipe/exception/open item gets its `MAP.md` line, a user-visible change its `CHANGELOG.md` line.

## Owner conventions

- Windows accent by default (orange kept as a choice), soft and hover tints transparent (`AccentService`); theme and accent are Left/Right gallery cards, not drop-downs.
- Cards: label left, control right; Up/Down between cards, Left/Right edits or walks a row's parts, Enter activates; half-width cards (`Half = true`) pair two per row, Up/Down follows reading order.
- Honest effects reporting on every row and FX window (`EngineStatus`: running with its delay, waiting, not installed, failed and why). Effects an engine does not run (`FxKind.Engines`) are stored only and the UI says so; VST3 on Equalizer APO rows is kept, not run; a VST2 plug-in Equalizer APO runs is said to run with the settings saved in OmniControl and an unknown delay; plug-ins that won't load are refused with one sentence (`PluginLoader`); for the master in Equalizer APO, only that the chain was sent.
- Windows' icon cache may show the old icon until Explorer restarts.

## Global design principles (every control and page)

Implement each once in a shared place (`Shared/Ui/Styles` style, shared row template, attached property, start-up class handler); a control that behaves differently means the shared piece is fixed, never the control.
1. **Hover/focus** from master styles; hover never moves or resizes text. Inside a container a control takes `BrushControlFill`, `BrushControlTrack`, `BrushControlEdge` (never `BrushHover`, `BrushSidebar`, `BrushDivider`), so its fill and edge differ visibly from every container fill in both themes.
2. **Values change live**; no Apply step. Only choosing a different action needs a confirm.
3. **Every value control works four ways:** mouse; keyboard (Left/Right or Up/Down); wheel while hovering the control itself (`ValueWheel`; for a ‹ value › selector only over its arrows and value, `ValueWheel.Selector`); for numbers, typing — double-click or Ctrl+Enter opens a box, clicking away/moving focus/Tab applies, Esc cancels, Enter applies and confirms and never starts typing.
4. **Double-click a slider resets it** to its defined default (`SliderReset`). Knobs: click without drag or right-click types, double-click resets, drag turns; the value box under a knob types on click or double-click and never resets (`Controls/Knob`, `NumberText`).
5. **Shared settings** (the same gesture action on many areas) are edited once and applied to all by a switch on by default; off edits one item.
6. **Steps mean real amounts** ("Change per wheel notch" = the actual change, default 5 %).
7. **Placement:** labels left, control centred in its card; colour dots and gallery items are clickable as well as steppable.
8. **Compact density:** one base text size (`ControlContentThemeFontSize`), tight shared padding, no dead space; text wraps before a card grows.
9. **Feedback near where it is wanted:** a page's own state shows only on that page.
10. **Safety:** anything that launches programs or sends keys by itself is rate limited and always releases what it presses.
11. **Calm wording:** one plain sentence; detail in a tooltip, docs or log; red only for a real failure, yellow sparingly, one tag per fact. An unexpected error: one sentence with the next step, "Copy details" and the log path, never a raw exception.
12. **No keyboard instructions on screen** (no footer strips or paragraphs of keys); keys are learned from tooltips, one "Keyboard shortcuts" item and controls behaving as expected. A status line only when it carries real state: one thin line, small font.
13. **Fit more, clutter less:** half-width cards where two fit, one toolbar row, a control beside what it affects, smaller type for secondary values, tooltips for explanations, saved space to what the user works on; group and align related controls; check the narrowest window and say what kept it uncluttered.
14. **One design language:** the same kind of thing looks the same and sits in the same place everywhere (presets = `PresetPicker` on the group's header line; Restore defaults = the pill right of the section title; a fact = `Border.tag`; a choice among a few = the shared pop-down list). A new case that does not fit extends the shared pattern and every user of it; when you touch a page, check its siblings and fix or list (`MAP.md`) the same inconsistency.

## One master list (owner)

Everything the app can do, show or be searched for comes from ONE master list per kind (`MAP.md` "Master lists"); adding an action, state, setting, device, gesture area, OSD element or hardware watch is one registration by its owner and appears everywhere it applies. Consumers read the live list and follow its changes, never a copy; extra data (category from the page's `Title`, group, scope, icon, flags such as `NeverBlock`, `Common`, `ConfirmRun`) lives on the entry, never in a side list or matched from label text; no second copy of an action. A changed id is announced once (`Move`) and each owner of stored references rewrites its own. Actions run only through the registry's one run path (gate, `RunChain`, chains stop at `Timing.AutomationChainMax`); block rules are enforced only at its gate. Windows' hardware announcements come only from `Core/Engine/HardwareSignals` through `HardwareWatches`; never add another device or display listener. What another PC may use is exactly the entries flagged `Common`; its requests pass the same run path after a `Common` check and a launch limit; crypto only in `OtherPcs/PcCrypto`, the pairing key only in Windows' credential store. If a second hand-written list is ever needed, the design is wrong: fix it first.

## Lessons from the audits (check before you write)

- Pop-downs sit in the logical tree of their control: style a container's own items with the child selector (`ListBox.rows > ListBoxItem`); size glyphs after the generic `Path.glyph` (the later style wins).
- The shared piece probably exists (`MAP.md`); no per-control wheel, reset, typing, hover or focus handler. No new static mutable state, caches or "currently editing" fields in shared helpers; unsubscribe and dispose what you create.
- Every entry point (action, timer or thread callback, `async void` handler, start-up and shut-down step) catches, logs and reports its own failure through `Shared/Services/Guard.cs`; shut-down steps go through `ShutdownSteps` at their stage.
- Saves are atomic through `AppDataStore`; never overwrite a file you could not read; a failed save or load is logged and reported once.
- `ShellViewModel.Report` (the context's `Report`) is the one thread-safe status path, given by constructor; never wrap it in a UI post.
- The mouse hook callback only classifies and enqueues: no UI Automation, I/O or waits inside it; slow work goes to the work queue, answers come from a cache kept fresh elsewhere.
- Services keep their settings: others call intent methods, never edit `service.Settings` then `Apply`/`Save`; a service needing facts from another takes an interface or `Func`. What a class needs comes by constructor, not a settable property.
- Bindings resolve at run time: never a namespace prefix inside a binding path (`$parent[fx:X]`, `((vm:Y)DataContext)` crash the window); grep touched `.axaml` for `\$parent\[[a-z]+:` and `\([a-z]+:[A-Za-z]+\)`.
- After a scripted multi-file edit, grep or diff the result; use the Edit tool for anything with quotes, pipes or newlines.

## Lean, light and fast (STRICT; every agent, every change)

Breaking one of these is a defect, the same as a crash. Before finishing, check your diff against each line and say in your report how you kept to them.
- **Least code/text/size.** Shortest code that does the job (see rules 10–13); docs are `AGENTS.md` and `MAP.md` only, no handover logs. No new NuGet package, native file or asset without stating its installed and compressed size and the owner's OK; prefer Windows' own APIs. Builds stay self-contained, trimmed for publish (`LeaveOutOfPublish` in the csproj); anything loaded by reflection or COM must keep working trimmed (say how). Never add Linux/macOS pieces, extra fonts, symbols or language files.
- **No idle work.** Timers, polls, meters, captures, hooks, ETW, sensors and redraws run only while something on screen, a rule or an enabled feature needs them (derived from the owners, never a side list). Prefer Windows' events over polling; if unavoidable, the slowest interval that works, from `Timing`. Hold `TimerResolution.Hold()` only while animating.
- **UI thread stays free.** No disk, registry, COM, WMI, process lists or network on it; saves via `AppDataStore.SaveSoon`, logs via `LogWriter`. Expensive views are built on first open and let go when hidden.
- **Light memory.** No unbounded or static caches; release COM objects, handles, icons, subscriptions; no pinning memory, no `SustainedLowLatency`, no process-wide priority raise.
- **Use the cores when it pays.** Heavy independent work (audio DSP, scans, analysis, file reads) on workers at normal or lower priority; the audio thread never allocates, locks or waits on its normal path and always has a safe fallback.
- **Prove it cheaply.** Estimate RAM, CPU, start-up and size effects in your report; anything that could cost more than it saves goes to the owner first.

## How jobs are run (owner)

- **Orchestrator** = the agent talking to the owner. On every new request it reviews running and queued jobs: overlap or contradiction (change a brief or message the agent), same files/subject (same agent if its context is small, else queue directly after, never parallel), combinable jobs, an agent's context too large (start fresh); re-orders to avoid rework (shared piece first); states the outcome to the owner in one or two lines; keeps the queue in the task list.
- **Parallel only when safe:** only if jobs share no files (shared docs get small Edit-tool edits only) and none needs another's uncommitted work; otherwise they queue. A parallel agent works in its own git worktree, only compiles there, never builds into, stops, deletes or launches the real app. When all report, the orchestrator merges, builds once, relaunches.
- **Model by complexity, lean** (a model the owner names wins). Ceiling: never above Sonnet medium or Opus low. Haiku low: lookups, renames, wording, a default value, doc-only edits, a one-file change with an obvious place. Sonnet low/medium: normal fixes and small features inside one page or service following an existing pattern. Opus low: features across several files or layers, UI to a mock-up, shared master pieces, root-cause hunts, engine/audio/Win32 work, a fix that already failed once.
- **Briefs** start with "Read AGENTS.md first and obey it", are complete (files, pattern to copy, what done looks like, mock-up path) and end asking for what was done, skipped and unverified.
- **Mock-up discipline (every agent, any harness).** Build only to an owner-approved mock-up (rule 1), part by part. The brief's checklist carries its exact values per part (colour, size, line, placement, exact wording) and the nearest existing example to copy; the report answers each numbered item yes/no. Nothing new and nothing missing: no page, section, setting, wording, control, style or behaviour the mock-up does not show, and no dropped part — an unbuildable part stops and is reported as a gap, never replaced by an invention. A master style that cannot do a part yet is a reason to extend that shared style (and every user of it), never to change the design; a real deviation needs the owner's OK *before* it is built, never only a note afterwards. An unclear behaviour rule is asked or listed as skipped, never decided silently. "Done" means every checklist item matched, re-read against the mock-up before reporting (compiling alone is not done); the orchestrator checks part by part and sends missing or wrong parts back.
- **Ember-only limits (other agents skip this bullet).** On top of the mock-up discipline: Ember never invents a design and is not used for open-ended design or a fix that already failed once; it works only in its own git worktree, only compiles there, and never builds into, stops, deletes or launches the real app; it never edits `AGENTS.md`, `MAP.md` or `CHANGELOG.md` (the orchestrator does those).
- **Ember as orchestrator (only when the owner explicitly hands over; then the worktree/compile-only/no-launch limits above are lifted, everything else in this file binds in full).** Verify, never assume: a thing is done only when a command's output proves it (a build's "0 errors", a running process listed, a release's assets listed by name) — never from memory, intention or a previous run. Read failure logs yourself and name the failing step and line before changing anything. Never hand-edit a generated file's internals (package locks, hashes): regenerate it with the exact tool/SDK version the consumer uses. Never change a test to match the code until you have proven from the code, its comments and `MAP.md` that the code's new behaviour is intended — say that proof in the report; if you cannot prove it, stop and ask. Never overwrite, revert or commit another agent's uncommitted work; untracked `docs/mockups/` files are other jobs' property — leave them out of every commit. Any re-tag, re-push or retry of a failed release is reported to the owner with its cause before it happens, and the release is finished only when the published release page lists Setup, Portable and SHA256SUMS. Windows admin (UAC) prompts can only be accepted by the owner: say so and wait, never claim an app or Setup was launched until its process is listed. The version bump after a release happens only after the published assets are verified, touches only `<Version>` in the csproj, and is committed and pushed on its own.
- **Reports** are short, plain English, no code talk: deviations and skipped parts first as their own list, then what was done, skipped and unverified.
- **Test once, at the end:** agents run no tests and launch nothing; their only check, when they changed code, is a compile with `-o` into a scratch folder under `%TEMP%` (deleted afterwards). Tests run only when the owner asks, or once at the end of the queue when a job truly cannot be judged from code.
- **Autonomy:** the queue of approved jobs lives in the task list; when a job reports, the next starts at once. A turn ends only when the queue is empty, a real decision or an outward-facing approval (a push) is needed, or the owner stops it; requests made mid-work join the queue in order and are acknowledged.
- **No rebuild or relaunch until the whole queue has finished**, unless the owner asks.

## Versions, builds and releases (owner)

- The version lives ONLY in `<Version>` in `OmniControl.App/OmniControl.App.csproj` (read by `AppInfo`, `tools/setup.iss`, `tools/release.ps1`).
- Every fix or feature adds a line under "Unreleased" in `CHANGELOG.md`. On "upload": move those lines under the version already in `<Version>`, commit, push, run `powershell -ExecutionPolicy Bypass -File tools\release.ps1`, which only tags `v<version>` on the pushed, clean HEAD and pushes the tag; the `Release` workflow (`.github/workflows/release.yml`) then builds from that tag and publishes the GitHub release (always a full release: Setup, Portable, SHA256SUMS, build provenance attestations). `release.ps1 -Local` builds and publishes from this PC, only when the owner asks. Several fixes may share one bump. After the release is published, bump `<Version>` to the next number (0.1.9 is followed by 0.2.0), commit and push.
- Licence GPLv3 (`LICENSE`). Never commit private info (names, emails, IPs, credentials, personal scripts); check the staged diff before every push.
- Always self-contained (`RuntimeIdentifier` win-x64, `SelfContained` true); never framework-dependent, never ask the owner to install a runtime.
- Fastest build: only `OmniControl.App`, Release, incremental (a full `--no-incremental -p:Deterministic=false` only when Smart App Control blocks the new DLLs). The check is: it compiles, loads and launches. No tests unless asked; the Setup is built and launched at finish (rule 2), release packaging only for an upload. The .NET SDK is in `%USERPROFILE%\.dotnet` (put it on PATH).
- Kill, then build: OmniControl runs as admin, so end it with `Start-Process taskkill -ArgumentList '/F /IM OmniControl.exe' -Verb RunAs -Wait` (the owner accepts UAC), check it is gone; never ask the owner to close it.
- One build on disk: delete every `bin` and `obj` (repo `bin\`, `OmniControl.App`, `OmniControl.Core`, tests), build into `OmniControl.App\bin\Release\net10.0-windows10.0.19041.0`, then build the Setup installer (`tools/setup.iss`) from it and launch the Setup — never launch the `bin` copy of `OmniControl.exe` directly, and never leave or launch another copy.
