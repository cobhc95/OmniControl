# OmniControl map

Where everything lives, the master pieces to reuse, how to add things, the allowed exceptions and the open items. Rules: `AGENTS.md`.
Keep it current in the same task: a new folder, master piece, recipe, exception or open item gets its line here (one line per folder, never per file).

## Layers (dependencies point down only)

```
OmniControl.App/Shell             start-up, main window, sidebar, search, footer; lists the feature modules
OmniControl.App/Features/<X>      one folder per feature: services, actions, states, pages, Timing.<X>.cs, its <X>Module.cs
OmniControl.App/Shared            what features share: Contracts, Ui (Controls, Pages kit, Restore, Styles), Services, Dialogs, Presets, Scripts
OmniControl.Core                  Windows access only (DDC/CI, Core Audio, WMI, WASAPI, VST hosting, hooks, Win32). No UI, no Avalonia, no settings files
```

- Core never references App; Shared should name no feature (some still do: open item); a feature reaches another only through a narrow interface or a `Func`/`Action` given by the shell (`IActionRegistry`/`IActionCatalogue`/`IActionRunner`, `IStateRegistry`/`IStateCatalogue`, `IOsd`, `IPresetGroups`, `IHardwareWatches`, `IPairedPcs`, `IPcBook`, `ActionGateSlot`).
- A view-model never calls Win32/COM (it calls a service or Core); views hold layout and input wiring only.
- Start-up: `Program.cs` -> `App.axaml.cs` (theme `ThemeChoices`, surfaces, accent) -> `Shell/ShellViewModel` makes the shared registries, then each module's `Register(FeatureContext)` in start-up order (this order decides the master lists' order and the mouse hook's handler order), then each page in sidebar order registers its entries (`FeaturePage.Registers`, through its module's services), then `PagesMade`. A page's view-model is made at its first use (opening, a search, Restore all, "Show in OmniControl", a tab asked for; `Shell/PageSlot`) and kept for the run; the sidebar, search's page list, pickers' sections, preset manager and restore actions read only its static `PageInfo`. Volume and Displays are still made at start-up (`FeaturePage.AtStart`, open item). `App.axaml` holds only the shared card rows' templates and the app-wide sizes.
- Shut-down: `Features/ShutdownSteps` runs every owner's steps in `ShutdownStage` order, each guarded; steps that put Windows back (displays, pointer, hook, effects) keep their stages; plug-in teardown is last.
- Saved files: `%APPDATA%\OmniControl`, one `DataStore` per file in `Shared/Services/DataStore.cs`, read and written only through `AppDataStore` (atomic). Every settings store saves with `AppDataStore.SaveSoon` (text taken at once, written by a worker after `Timing.SaveSoonDelay`, so no disk on the UI thread); only journals that must be on disk at once (display recovery, pointer and trackpad backups, swap trial, Windows OSD record, wake undo, engine journal, power journal, restore snapshots, an import's files) use `Save`/`SaveText`. A read, direct save or delete of a store writes or drops the waiting text first, and `FlushSaves` runs at shut-down (`ShutdownStage.Flush`), on an unhandled exception, before a backup or import, and after a restore. A damaged file is kept as `name.bad.json` and said once at start-up (`AppDataStore.TakeDamaged`). Logs: `AppDataStore.AppendLog` queues to the one background `LogWriter` (roll-over at `Timing.LogMaxBytes` to `name.old.txt`; `FlushLogs` at exit and on an unhandled exception).
- Idle work: a view that wants fresh values holds a handle (`Shared/Services/HoldCount`): `MixerService.WatchClosely` (Volume page on screen, FX window, tray panel: 2 s scans, else `Timing.MixerRefreshIdle`), `MouseService.WatchPresses` (Mouse page), `SimulationSetup.WatchClosely` (Devices page: adb every `Timing.DeviceSimLive` also while a device has a simulation method, the emulators' memory only while on screen, the emulator search once then at each page open). Smart Devices' periodic auto-check timer runs only while a device has a repeating auto-check, and Python is probed at start only when a device uses Scripts. The autoscroll block's worker (`Core/Engine/Mouse/AutoscrollWatcher`) sleeps until the hook says the pointer moved (`MouseHook.PointerMoved`), rests after `CoreTiming.AutoscrollRestLooks`, and runs only while the block is on and the middle button is not mapped on every layer. The OSD's windows, keep-warm redraw and media watcher exist only while the OSD (and a media element) is on. Spinners animate only with the `.spinning` class, bound to the state that shows them. `ProcessPower.Compact` is a background (never blocking) collection. Fine 1 ms timers only through `Core/Engine/TimerResolution.Hold()` (recording, OSD on screen; meters need none). The mouse hook is installed only while a handler's owner says it needs it (`MouseHook.AddHandler(handler, needsHook)`, `Recheck` from `InputModule`); its last owner, `Input/Mouse/BackForwardGuard` (Back/Forward over OmniControl or the desktop), always does, so in practice it stays installed; the touchpad watcher only while `mouse.NeedsTrackpad || rules.NeedsTrackpad`. The main window holds only the open page's view (`Shell/PageHost`: built when the page shows, let go when another page or the search results show, `ShellViewModel.ShownPage`; how far it was scrolled is kept in its view-model, `PageViewModel.Scroll`, and put back; a page stops its work in `OnOnScreenChanged(false)`); inside a page, a part shown by a switch (a card's other layouts, a group's body given as its `ContentTemplate`, a subgroup's cards, the Volume page's Easy and Advanced views and Mixer and Wiring tabs) is a `Pages/CardLayout`, built while shown and let go when hidden. `ProcessPower.Compact` gives memory back once the window has been hidden for `Timing.HiddenSettle` (also `Timing.CompactAfterStart`). After `Timing.UiReleaseAfterHidden` hidden (counted from the hide, never while minimised: `SetWindowShown(shown, hidden)`) the shell raises `ReleaseWindows`: `WindowLifecycle` closes the main window (made again by the next showing at its place, size and page, `MainWindow.Placement`; the app ends only by its one exit path, `ShutdownMode.OnExplicitShutdown`) or, while a window it owns or the close question is open, gives the reason, which timing-log.txt gets, and the shell asks again after the same wait; the shell lets go of the hidden Actions and hotkeys window (`SingleWindow.Release`), then `ProcessPower.CompactAfterRelease` (Skia's caches emptied, a background full collection, the large objects marked for compaction at the runtime's own next blocking collection; never a forced blocking one, which would stall the hook and the audio thread; working sets are never trimmed) `Timing.UiReleaseCompactAfter` later unless sound runs through the process (`VolumeModule.StreamsAudio`, `ScreenshotModule.Records`). Always instant (owner): the OSD, the mouse and keyboard hooks, the audio engine and the tray panel (`TrayService` builds it hidden after start-up and never lets it go). Page view-models, made at their first use, stay; a view that listens to its model does so only while attached (`ChoiceChip`'s pattern, also a control fed by a binding such as `LevelMeter.Model`), and no static holds a control (`RowEditing` marks the slider being adjusted with its `active` class), so a released window is never held. `UiTiming.Memory` writes the memory (Task Manager's figure too, `ProcessPower.PrivateWorkingSet`) and the visuals of the open windows to timing-log.txt `Timing.MemoryLineAfterStart` after start, at the hidden settle and after the release (with the visuals before it), and `Timing.UiReleaseLeakCheck` after the release whether the let-go main window was collected. The Resources poller (`ResourceMonitor.Need`) reads only the parts its needs ask for (`SampleParts`: page all, gadget its shown readings, rules the watched ones, adapters only while the adapter menu is open); sensor readings come from Windows' own sources (`Core/Engine/Resources/WindowsSensors`: GPU and disk load from performance counters, graphics temperatures from the graphics kernel, drive temperatures from the storage temperature query, ACPI thermal zones), each opened at its first need; LibreHardwareMonitor (`LibreSensors`, its assembly loaded only then) opens, with only the groups needed, for a reading Windows gives none of now, a chosen Hottest sensor of its own (only the group it was last found in) and the sensor menu while open (`SensorReader` decides); updated at most every `CoreTiming.SensorEvery`, temperatures every `CoreTiming.TemperatureEvery`, drives every `CoreTiming.StorageSensorEvery` while a disk reading is shown, else `CoreTiming.StorageTempEvery`.

## Recipes

- **Feature module:** `Features/<X>/<X>Module.cs` implementing `IFeatureModule`; in `Register(FeatureContext)` make services, register actions, states, watches, preset groups, `context.Imports.OnReload(store, ...)`, `context.Shutdown.Add(stage, what, step)`; offer `Pages` and `Templates`; add the module to the shell's start-up list (and the sidebar list if it has pages).
- **View:** bindings are compiled (`AvaloniaUseCompiledBindingsByDefault`): every view, data template, and style or control theme whose setters bind names its `x:DataType`; a view's own properties through `RelativeSource={RelativeSource AncestorType=prefix:View}`, the parent's view-model through `$parent[ItemsControl].DataContext.X` (never a prefix inside a path).
- **Page:** `<Name>PageViewModel` (derives `PageViewModel` with its `public static readonly PageInfo Info` (title, icon, `NavGroup`, keywords, `RestoreKey`) passed to `base(Info)`; `SearchEntries` via `Entry`, `OnShown`, `OnOnScreenChanged`, `KeyHelp`) + `<Name>Page.axaml` in `Features/<X>/Pages`; one `FeaturePage(Info, make)` in the module's `Pages`, one `ViewTemplate.For<VM, View>()` in its `Templates` (never `App.axaml`). The view-model registers nothing: the page's actions, states, OSD elements and preset groups are registered by its module's services in `FeaturePage.Registers` (a page-only action, such as Other PCs' tab actions, forwards to the page when it exists). Tabs: override `Tabs` with a `PageTabs` shown by `PageTabsView`; anything opening the page at a tab calls `context.OpenPage(Title, tabName)`.
- **Action:** `context.Actions.Register(new HotkeyAction(id, title, Title, keywords, run) { ... })`; a level: `HotkeyAction.ForLevel` both directions; changing devices: one action with a device source + `RefreshDevices`; directions of one thing share a `Family`; a renamed id: `Move`; a standard Windows shortcut that does the same: `KeyEquivalent` (a built-in mouse action: `KeyEquivalent` on its `MouseActionCatalog` line).
- **State:** `context.States.Register(new StateEntry(...))`; call `Notify(id)` when it may have changed.
- **Hardware watch:** `context.Hardware.Register(new HardwareWatch(id, name, signals, refresh, looksStale))`; name it in the action's `HardwareWatch`.
- **OSD pop-up:** `context.Osd.Declare(name, icon)` once, then show through `IOsd`.
- **Preset group:** a provider deriving `Shared/Presets/PresetProvider` (the defaults said once; `ListPresetProvider<T>` for a `PresetList` after built-ins, entries worked out once per change) + `context.Presets.Register(new PresetGroup(id, section, title, provider))`; show it with `PresetPicker` on the group's header line.
- **Data store:** a `DataStore` line in `DataStores` (with `Import`/`MachineSpecific`/`NotImported`); the settings class loads and saves only through `AppDataStore`; reload on import via `context.Imports.OnReload`.
- **Setting slot:** a field in `AppSettings` read and written by the feature through `context.Settings.Slot(s => s.X, (s, v) => s.X = v)` (`ISettingSlot<T>`), never `AppSettings.Current`.
- **Timing:** a named value in `Features/<X>/Timing.<X>.cs` (`public static partial class Timing`, namespace `OmniControl.App.Shared.Services`, so calls stay `Timing.X`); Core values in `Core/CoreTiming.cs`.
- **Undo in a window:** its view-model owns an `UndoHistory`, calls `Record(name, undo, redo, mergeKey)` after each change (undo and redo through the same paths as the UI; recording during them is ignored) and `Clear()` when the window closes; the window's `Menu` gets `<c:EditMenu History="{Binding ...}" />`.
- **Restore defaults:** the page implements `IRestorable` (`Shared/Ui/Restore`), the pill sits at the right of the section title.
- **Style (cost per control):** every global style whose last part names a control type is tried, with its own watcher and setter objects, on every control of that type in every window, matching class or not; so a size or other fixed value is `{StaticResource}` (only theme, accent and surface brushes are `{DynamicResource}`), a piece of one window or control is styled in a file that window or control includes (not `App.axaml`), and a descendant selector names an ancestor by type or uses `>` rather than a class ancestor (`Grid.x TextBlock` is watched on every text in every grid). A Button variant is a ControlTheme in `Styles/ButtonThemes.axaml` (BasedOn Fluent's Button theme), picked by one `Button.x` style that sets `Theme`, so other buttons try one style instead of all its own; the button keeps its class for its child selectors (a theme cannot hold one, they stay in the master files). A theme ranks below every global style, so only a variant whose styles all came before the master hover in `ThemeButtons.axaml` (or that the hover leaves out) is a theme, with its styles in their old order.
- **Apps scope:** store an `AppScopeSetting?`, make the model with `AppScopes.Group`/`.Card`, ask `AppScopeGate.Allows` before acting.

## Exceptions (allowed on purpose; the owner may overrule)

Hard-coded:
- `Icons/IconLibrary.All` and `Styles/Icons.axaml` are data (the master list itself); `Tray/TrayDefaults` types default ids as tray.json holds them.
- `Screenshot/ImageBitmaps` opacity mask uses `Colors.Black` (only its strength counts); `StrokeMark.PartLength` 64 is a drawing detail.

## Known limits (not bugs)

- Plug-ins load only from a local drive path (never a share or a mapped network drive), and while OmniControl runs as administrator only from folders only administrators can change (`PluginLoader`, one sentence otherwise); a plug-in's own DLLs are looked for only in its folder and System32 (`PluginLoader.LoadLibrary`, also for VST3 before NAudio loads it), so one that needs a DLL from PATH is refused. A restore from a backup leaves out effects' plug-in and impulse-response files and their states, as an import from another PC does (`DataStore.NotImportedInside`). Equalizer APO's config files are written only when neither they nor the folder is a link (`Core/Engine/PlainFile`; each write opens the file itself, never a link's target, and checks that same handle, `PlainFile.OpenToWrite`).
- Effects an engine does not run (`FxKind.Engines`) are stored only and the UI says so; VST3 plug-ins on Equalizer APO rows are kept, not run; a blend's dry part is not delayed to match a plug-in's latency.
- Pan needs Windows to allow per-channel session levels (`AudioSession.CanPan`); per-app output uses an undocumented interface (`CoreAudio.Routing.cs`); hiding Windows' OSD is best-effort (`WindowsOsd`).
- The mouse hook cannot act on programs running as administrator unless OmniControl runs as administrator; it never runs on the secure desktop (UAC prompt, Ctrl+Alt+Del, lock screen), never sees a mouse passed straight into a virtual machine (USB pass-through), and a program that reads the device below Windows' input (some anti-cheat drivers) still gets the original button. Another program's low-level mouse hook installed later (XMouseButtonControl) is asked first and may take a button before OmniControl sees it.
- Actions sent to a remote-input window as keys: only mouse buttons, middle-click and trackpad gestures (wheel gestures act on this PC's screen areas, custom rules decide their own steps, keyboard hotkeys already reach the remote when it has the keyboard); keys go into a remote window one event at a time, `CoreTiming.RemoteKeyGapMs` apart, by scan code (a shortcut of four keys takes about 45 ms); where Remote Desktop keeps shortcuts on this PC (keyboardhook 0, or 2 while not full screen: no title bar and covering its monitor, `WindowQuery.CoversItsMonitor`) Alt+Tab and the like go as its own replacements, while Windows-key shortcuts have none and act on this PC (the mouse log says so once per run); the keyboardhook is read from the .rdp file named on mstsc's command line, else Documents\Default.rdp, else Windows' default 2, so a session started another way may be judged wrongly; Windows App / msrdc has no swaps (its setting is not in a file); keys held while a button is held and wheel-gesture keys are sent as before (all at once); the remote's volume keys move by its own step, not the action's.
- Other PCs is basic only (LAN or Tailscale/ZeroTier address); no relay; Windows Remote Desktop covers more. Pairing and the link (protocol `PcProtocol.Version` 3) need the same version on both PCs; an older PC is refused with one sentence when pairing, and paired PCs on different versions just show offline.
- While OmniControl runs as administrator, what it opens through the shell (`NormalRights.Open`) is handed to a short-lived normal-rights copy of itself, so a file or address Windows then fails to open is not reported; with Explorer not running, or Windows' Secondary Logon service off (it starts a program with another token), nothing is started and one sentence says so.
- Equalizer APO is its own program: OmniControl ships its official 1.4.2 x64 installer unmodified (`third_party/equalizer-apo`, about 12 MB, copied to the app folder's `equalizer-apo\`; `ApoInstaller` checks its pinned SHA-256 and holds it open while it runs) and uses Equalizer APO's own installer, Device Selector, uninstaller and Installed apps entry as they are. Setup's task "Equalizer APO", on by default, runs it with NSIS `/S` after the files unless it is installed (its Uninstall entry, or its InstallPath holding EqualizerAPO.dll); `/S` skips its pages (its default folder, its update checker ticked) but still opens its Device Selector (`/i`) and waits for it, then its device check and a "can be reopened from the Start menu" note; when that check fails its installer only sets NSIS's reboot flag, which a silent install never acts on, so Setup's finish page and the app's result say to restart Windows if the check showed a device that didn't start. The app's "Install Equalizer APO…" (Portable too) runs the same file the same way (one administrator prompt) and the first use of a master effect only offers it, once per run, after the user changed the master's effects or the routing; "Equalizer APO devices…" opens its Device Selector. OmniControl reads, never writes, its registration and which devices have it in their FxProperties, and writes only its own chain into the config folder Equalizer APO's ConfigPath names; whether it really started on a device is Device Selector's check, which OmniControl does not run. OmniControl's uninstall leaves Equalizer APO installed.
- Download limits (`Core/Engine/Resources/DownloadShaper`) need Windows Packet Filter (`ndisrd.sys` and its `ndisrd` service; its official Windows 10+ x64 driver files, taken unmodified from its MSI, ship in `third_party/windows-packet-filter/driver`, copied to the app folder's `windows-packet-filter\` by the App csproj; Setup's task "Install Windows Packet Filter", on by default, runs Windows' `netcfg -v -l <inf> -c s -i nt_ndisrd` after the files unless the driver is there, a failure only shows one line; while OmniControl runs as administrator the first download limit set, or a saved one at start-up, installs it the same way (hidden, no prompt) after checking the files' pinned SHA-256 in `PacketFilterSetup`, and "Install Windows Packet Filter…" shows only as a retry after a failure; both record it under `HKCU\Software\OmniControl`, and uninstall runs `netcfg -v -u nt_ndisrd` only with that record). With neither the network service nor administrator rights Network traffic control shows only `NetworkLimits.UnavailableLine` and, on an installed copy, "Install…" (a portable copy says the service needs the installed version): nothing is read (no per-program ETW session) or put into Windows. The driver is opened only while a limited program owns ports (port tables read every `ResourcesShaping.PortsIdle` while none does, every `.Ports` while one does, `Timing.ResourcesShaping`), every Ethernet-style adapter tunnelled, never an IP-medium WinTun tunnel (Tailscale, WireGuard: its frames cannot be shaped and its traffic could be lost, so limits do not apply there) (new ones through the `resources.download-adapters` hardware watch), and only packets to the limited programs' ports (its filter table) reach OmniControl, so a new connection runs unlimited until the next look; IPv6 packets with extension headers pass unlimited; `NetworkLimits.Download` says what runs. The Resources page's "Packet filter" switch (on the Network traffic control group's header, left of its Apps chip; `ResourcesSettings.PacketFilterOn`, not in presets; the group's Restore defaults turns it on) is for conflicts with other software: off, the shaper never opens the driver (download limits kept, shown as "Packet filter is off"; upload limits and blocks unaffected) and `PacketFilterSetup.Attach` detaches its binding from every adapter (Windows' own `Disable-NetAdapterBinding`, hidden ones too, through the elevated helper, read back over WMI); on attaches all again. A refused prompt or failure turns the switch back with one sentence. While off and OmniControl is administrator, start-up and the `resources.download-adapters` watch detach it from adapters Windows added (no prompt); without administrator a new adapter keeps its binding (unused) until the switch is changed.
- Network service (threat note): a demand-start LocalSystem service (`OmniControlNetwork`, the app folder's `OmniControl.exe --network-service run <SID>`) that only Windows' service manager can run (started any other way it refuses). Its pipe `OmniControl.NetworkService` allows only the installing user's SID (read, write) and SYSTEM, denies NETWORK, is created first-instance-only (a squatted name makes the start fail), and OmniControl talks on it only after checking the process at its other end is the running service (`NetworkServiceSetup.ServerProblem`: the pipe's server process id against the service's, else one line and nothing sent), one client at a time; the user may only start, stop and query the service. Requests are a fixed, versioned list (`NetworkPipe`, unknown fields or names refused, 4 KB in, 512 KB out, 256 programs): a path must be a drive-letter `.exe` outside the Windows folder, without stream, wildcard or control characters, made whole, and exist for a Set or Block; limits 1 KB/s to 1 GB/s; nothing is run, opened or written by path, the path only names a firewall or QoS rule and a program to shape. Fail-open: everything leaves Windows when the client disconnects or the service stops, a crashed run's rules leave at the next start, and it stops itself after `Timing.NetworkServiceIdle`. The exe it runs cannot be swapped by its user: Setup installs for all users into Program Files, and `NetworkServiceSetup.Install` (also when Setup asks) refuses unless `CanServeFrom` reads from the access lists that only SYSTEM, administrators and TrustedInstaller own and may change the exe, its folder, what it holds (inherited rights included, and for the service and the sign-in task every file and folder under it, each with its own list: `wholeFolder`) and every folder above it, so a portable or per-user copy never gets the service. What remains: the user it serves can block or limit any of their programs (Windows' own excepted) without an admin prompt.
- Install: Setup (administrator) puts OmniControl for all users into `Program Files\OmniControl`; settings stay per user in `%APPDATA%\OmniControl`, and the start-up entry, the Packet Filter record, the sign-in task's settings file and the service's user are those of the account Setup runs as (an administrator's own account when Setup is elevated with another account's password; the app's own "Install…" then puts the service on its user). Setup never starts cmd or an OmniControl.exe from a user-writable folder while elevated: it sets the running copy's quit event (`SingleInstance`) itself and finds running copies and the service's state with `tasklist.exe` and `sc.exe` from System32. Moving from the per-user install of 0.2.3 and earlier: Setup closes OmniControl, runs its old uninstaller silently with the token of the person who started Setup (never elevated) and the Packet Filter record set aside (so the driver stays), deletes `%LOCALAPPDATA%\Programs\OmniControl` (only that usual folder), then installs and points the start-up entry, sign-in task and network service at the new exe; an unticked network service task removes a service left from before.
- Taskbar gadget placement (`Core/Engine/TaskbarSpot`, `Resources/Gadget/TaskbarGadget.Place`): only on the main taskbar (`Shell_TrayWnd`), never a second monitor's; Explorer's announcements (TaskbarCreated, its taskbar and light/dark setting changes) reach it only through `HardwareSignals` (`Taskbar`, `TaskbarSettings`), a new taskbar or scale gets a new window; the window is layered and shows only the picture `TaskbarSpot.Paint` gives it (the window drawn by `GadgetWindow.DrawInto` after each placement and hover-edge change), since a software-drawn child paints into the taskbar's own surface, which Windows 11's XAML taskbar covers; a tray area that grows or shrinks (new icons, clock, language) is followed at the gadget's next read, not by an event; when Windows refuses the child window (owned instead) it does not slide with an auto-hidden taskbar. Position Left (`TaskbarButtons.RunEnd`): the end of the run of the taskbar's own controls that starts at its left (top) end, read through UI Automation (Windows 11's Start, Widgets and program buttons are XAML, without windows of their own): with centred icons that is the Widgets button (or the taskbar's edge when it is hidden), with left-aligned icons the last pinned or running program; controls more than 24 px (at 100 %) apart end the run, controls wider than a third of the taskbar count as containers and are left out. It is looked at again only when the gadget places itself, at most every `Timing.ResourcesGadgetLeftLook` (and at once after a taskbar announcement or a change of position), so a program button that appears can sit under the gadget for up to that long; until the first look (and if UI Automation cannot read the taskbar) the gadget sits on the right. When the left run reaches the tray (many program buttons) the gadget is kept inside the taskbar and overlaps the buttons; a third-party taskbar (ExplorerPatcher, StartAllBack) or another layout of Windows' own may put other controls there. Space to the tray is also the space after the left buttons on Left. The tray icon is put back after an Explorer restart by Avalonia itself (it lets TaskbarCreated through to its own window).
- Sensors (RAM plan 2): readings come from Windows first, so they read as Task Manager does: GPU usage is the busiest graphics engine summed over programs (was the driver's "GPU Core" load); "CPU temperature" on Auto is the sensor library's CPU package (`TemperaturePick`: package or Tdie, then Tctl, then cores and CCDs), so the library's CPU group stays loaded while it is shown; the hottest ACPI thermal zone only when the library reads no CPU sensor (no PawnIO driver; then it is not asked again until the sources close, `Timing.ResourcesIdleClose` after no sensor reading is wanted); graphics and drive temperatures are what the driver reports to Windows (one value per adapter, whatever the driver calls its temperature; a drive or card that reports none falls back to the sensor library's core, then hot spot, memory and regulator sensors last, and a drive the library cannot read either stops asking it until a disk change); the Hottest sensor on Auto is the hottest of Windows' sensors, of the library's groups open for other readings, and of the library's only for a group Windows has none in; a Hottest sensor chosen before this change keeps the library's id and opens the library's group as before. Every temperature reading (each disk's too) can be set to any one sensor (`SensorMenu`); a chosen one that is gone reads as Auto.
- Gadget weather: Open-Meteo's rain chance is today's highest on the gadget (the hover tooltip can give the next hour's; sunrise, sunset and the next hours come in the same request); only Open-Meteo gives a next-hour rain chance, MET Norway gives no sunrise or sunset and OpenWeatherMap no next hours, so those tooltip lines are left out; MET Norway gives no feels-like or rain chance (high and low are the next 24 hours); OpenWeatherMap's free current weather gives no rain chance and its high and low are the current observation's range; "Use my location" needs Windows' location on for desktop apps. Places are sent rounded to two decimals.
- Rendering is Win32 only and in software (`Program.cs`: `UseWin32().UseSkia()`, `Win32RenderingMode.Software`): no ANGLE, Direct3D or GPU driver in the process (`av_libglesv2.dll` is left out of publish, 5.2 MB); transparent windows (OSD, tray panel, overlays) use Avalonia's redirection-bitmap path (Windows' blur-behind with an empty region), no Mica or acrylic; every frame is drawn by the CPU, so a large window on a 4K screen costs more CPU while it animates or scrolls. Text is the system font (Segoe UI), no font is bundled. Skia's image and blur-mask cache is held to 8 MB (`ProcessPower.LimitDrawingCaches`, its default 32 MB; Avalonia's `SkiaOptions` sizes only a GPU cache, unused here).
- Trade-offs approved for idle cost: the USB pop-up and "device connected" rules follow Windows' device notice through the hardware watches (about `Timing.HardwareDebounce` after the plug); the laptop brightness check read runs for `Timing.OsdBrightnessCheckFor` only when Windows' brightness event is listened to; the autoscroll answer is renewed without a new lookup while the pointer rests; the OSD keep-warm redraw is every `Timing.OsdKeepWarm` (30 s).
- In a published build the .NET framework assemblies (except CoreLib) lose their precompiled ReadyToRun code (trimming rewrites them), so a little more JIT at start-up; putting it back costs about 19 MB installed. Only the app (`OmniControl.dll`) and `Avalonia.Base` are precompiled (csproj `ReadyToRunOnly`): 4.8 MB more in the Setup, 13.8 MB installed; adding `Avalonia.Controls` would pass the owner's 5 MB limit (5.4 MB). `LibreHardwareMonitorLib` is precompiled too, past that limit by the owner's choice (1.2 MB to 2.5 MB installed, about 0.5 MB more compressed), so its sensors open with less JIT.
