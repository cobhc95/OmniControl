# OmniControl map

Where everything lives, the master pieces to reuse, how to add things, the allowed exceptions and the open items. Rules: `AGENTS.md`.
Keep it current in the same task: a new folder, master piece, recipe, exception or open item gets its line here (one line per folder, never per file).

## Layers (dependencies point down only)

```
OmniControl.App/Shell             start-up, main window, sidebar, search, footer; lists the feature modules
OmniControl.App/Features/<X>      one folder per feature: services, actions, states, pages, Timing.<X>.cs, its <X>Module.cs
OmniControl.App/Shared            what features share: Contracts, Ui (Controls, Pages kit, Restore, Styles), Services, Dialogs, Presets, Scripts
OmniControl.Core                  Windows access only (DDC/CI, Core Audio, WMI, WASAPI, VST hosting, hooks, Win32). No UI, no Avalonia, no settings files
```

- Core never references App; Shared should name no feature (some still do: open item); a feature reaches another only through a narrow interface or a `Func`/`Action` given by the shell (`IActionRegistry`/`IActionCatalogue`/`IActionRunner`, `IStateRegistry`/`IStateCatalogue`, `IOsd`, `IPresetGroups`, `IHardwareWatches`, `IPairedPcs`, `IPcBook`, `ActionGateSlot`).
- A view-model never calls Win32/COM (it calls a service or Core); views hold layout and input wiring only.
- Start-up: `Program.cs` -> `App.axaml.cs` -> `Shell/ShellViewModel` makes the shared registries, then each module's `Register(FeatureContext)` in start-up order (this order decides the master lists' order and the mouse hook's handler order), then the pages in sidebar order, then `PagesMade`. `App.axaml` holds only the shared card rows' templates and the app-wide sizes.
- Shut-down: `Features/ShutdownSteps` runs every owner's steps in `ShutdownStage` order, each guarded; steps that put Windows back (displays, pointer, hook, effects) keep their stages; plug-in teardown is last.
- Saved files: `%APPDATA%\OmniControl`, one `DataStore` per file in `Shared/Services/DataStore.cs`, read and written only through `AppDataStore` (atomic). A store changed often (mixer, OSD) uses `AppDataStore.SaveSoon` (text taken at once, written by a worker after `Timing.SaveSoonDelay`); a read, direct save or delete of that store writes or drops the waiting text first, and `FlushSaves` runs at shut-down (`ShutdownStage.Flush`), before a backup or import, and after a restore. Logs: `AppDataStore.AppendLog` queues to the one background `LogWriter` (roll-over at `Timing.LogMaxBytes` to `name.old.txt`; `FlushLogs` at exit and on an unhandled exception).
- Idle work: a view that wants fresh values holds a handle (`Shared/Services/HoldCount`): `MixerService.WatchClosely` (Volume page on screen, FX window, tray panel: 2 s scans, else `Timing.MixerRefreshIdle`), `MouseService.WatchPresses` (Mouse page). Fine 1 ms timers only through `Core/Engine/TimerResolution.Hold()` (meters, FX windows, recording, OSD on screen). The mouse hook is installed only while a handler's owner says it needs it (`MouseHook.AddHandler(handler, needsHook)`, `Recheck` from `InputModule`); its last owner, `Input/Mouse/BackForwardGuard` (Back/Forward over OmniControl or the desktop), always does, so in practice it stays installed; the touchpad watcher only while `mouse.NeedsTrackpad || rules.NeedsTrackpad`. The main window keeps the view of every page visited for the run, hidden while another shows or the window is hidden (`Shell/PageHost`; a page stops its work in `OnOnScreenChanged(false)`), and `ProcessPower.Compact` gives memory back once it has been hidden for `Timing.HiddenSettle` (also `Timing.CompactAfterStart`). The Resources poller (`ResourceMonitor.Need`) reads only the parts its needs ask for (`SampleParts`: page all, gadget its shown readings, rules the watched ones, adapters only while the adapter menu is open); the sensor library opens only for GPU, disk or temperature readings, with only those hardware groups, updated at most every `CoreTiming.SensorEvery`.

## Recipes

- **Feature module:** `Features/<X>/<X>Module.cs` implementing `IFeatureModule`; in `Register(FeatureContext)` make services, register actions, states, watches, preset groups, `context.Imports.OnReload(store, ...)`, `context.Shutdown.Add(stage, what, step)`; offer `Pages` and `Templates`; add the module to the shell's start-up list (and the sidebar list if it has pages).
- **Page:** `<Name>PageViewModel` (derives `PageViewModel`: `Title`, `Icon`, `NavGroup`, `SearchEntries` via `Entry`, `OnShown`, `OnOnScreenChanged`, `KeyHelp`) + `<Name>Page.axaml` in `Features/<X>/Pages`; one `FeaturePage` in the module's `Pages`, one `ViewTemplate.For<VM, View>()` in its `Templates` (never `App.axaml`). Tabs: override `Tabs` with a `PageTabs` shown by `PageTabsView`; anything opening the page at a tab calls `context.OpenPage(Title, tabName)`.
- **Action:** `context.Actions.Register(new HotkeyAction(id, title, Title, keywords, run) { ... })`; a level: `HotkeyAction.ForLevel` both directions; changing devices: one action with a device source + `RefreshDevices`; directions of one thing share a `Family`; a renamed id: `Move`.
- **State:** `context.States.Register(new StateEntry(...))`; call `Notify(id)` when it may have changed.
- **Hardware watch:** `context.Hardware.Register(new HardwareWatch(id, name, signals, refresh, looksStale))`; name it in the action's `HardwareWatch`.
- **OSD pop-up:** `context.Osd.Declare(name, icon)` once, then show through `IOsd`.
- **Preset group:** a provider deriving `Shared/Presets/PresetProvider` (the defaults said once; `ListPresetProvider<T>` for a `PresetList` after built-ins, entries worked out once per change) + `context.Presets.Register(new PresetGroup(id, section, title, provider))`; show it with `PresetPicker` on the group's header line.
- **Data store:** a `DataStore` line in `DataStores` (with `Import`/`MachineSpecific`/`NotImported`); the settings class loads and saves only through `AppDataStore`; reload on import via `context.Imports.OnReload`.
- **Setting slot:** a field in `AppSettings` read and written by the feature through `context.Settings.Slot(s => s.X, (s, v) => s.X = v)` (`ISettingSlot<T>`), never `AppSettings.Current`.
- **Timing:** a named value in `Features/<X>/Timing.<X>.cs` (`public static partial class Timing`, namespace `OmniControl.App.Shared.Services`, so calls stay `Timing.X`); Core values in `Core/CoreTiming.cs`.
- **Undo in a window:** its view-model owns an `UndoHistory`, calls `Record(name, undo, redo, mergeKey)` after each change (undo and redo through the same paths as the UI; recording during them is ignored) and `Clear()` when the window closes; the window's `Menu` gets `<c:EditMenu History="{Binding ...}" />`.
- **Restore defaults:** the page implements `IRestorable` (`Shared/Ui/Restore`), the pill sits at the right of the section title.
- **Apps scope:** store an `AppScopeSetting?`, make the model with `AppScopes.Group`/`.Card`, ask `AppScopeGate.Allows` before acting.

## Known limits (not bugs)

- Effects an engine does not run (`FxKind.Engines`) are stored only and the UI says so; VST3 plug-ins on Equalizer APO rows are kept, not run; a blend's dry part is not delayed to match a plug-in's latency.
- Pan needs Windows to allow per-channel session levels (`AudioSession.CanPan`); per-app output uses an undocumented interface (`CoreAudio.Routing.cs`); hiding Windows' OSD is best-effort (`WindowsOsd`).
- The mouse hook cannot act on programs running as administrator unless OmniControl runs as administrator; it never runs on the secure desktop (UAC prompt, Ctrl+Alt+Del, lock screen), never sees a mouse passed straight into a virtual machine (USB pass-through), and a program that reads the device below Windows' input (some anti-cheat drivers) still gets the original button. Another program's low-level mouse hook installed later (XMouseButtonControl) is asked first and may take a button before OmniControl sees it.
- Other PCs is basic only (LAN or Tailscale/ZeroTier address); no relay; Windows Remote Desktop covers more.
- Equalizer APO is its own program: OmniControl ships its official 1.4.2 x64 installer unmodified (`third_party/equalizer-apo`, about 12 MB, copied to the app folder's `equalizer-apo\`; `ApoInstaller` checks its pinned SHA-256 and holds it open while it runs) and uses Equalizer APO's own installer, Device Selector, uninstaller and Installed apps entry as they are. Setup's task "Equalizer APO", on by default, runs it with NSIS `/S` after the files unless it is installed (its Uninstall entry, or its InstallPath holding EqualizerAPO.dll); `/S` skips its pages (its default folder, its update checker ticked) but still opens its Device Selector (`/i`) and waits for it, then its device check and a "can be reopened from the Start menu" note; when that check fails its installer only sets NSIS's reboot flag, which a silent install never acts on, so Setup's finish page and the app's result say to restart Windows if the check showed a device that didn't start. The app's "Install Equalizer APO…" (Portable too) runs the same file the same way (one administrator prompt) and the first use of a master effect only offers it, once per run, after the user changed the master's effects or the routing; "Equalizer APO devices…" opens its Device Selector. OmniControl reads, never writes, its registration and which devices have it in their FxProperties, and writes only its own chain into the config folder Equalizer APO's ConfigPath names; whether it really started on a device is Device Selector's check, which OmniControl does not run. OmniControl's uninstall leaves Equalizer APO installed.
- Download limits (`Core/Engine/Resources/DownloadShaper`) need Windows Packet Filter (`ndisrd.sys` and its `ndisrd` service; its official Windows 10+ x64 driver files, taken unmodified from its MSI, ship in `third_party/windows-packet-filter/driver`, copied to the app folder's `windows-packet-filter\` by the App csproj; Setup's task "Install Windows Packet Filter", on by default, runs Windows' `netcfg -v -l <inf> -c s -i nt_ndisrd` after the files unless the driver is there, a failure only shows one line; while OmniControl runs as administrator the first download limit set, or a saved one at start-up, installs it the same way (hidden, no prompt) after checking the files' pinned SHA-256 in `PacketFilterSetup`, and "Install Windows Packet Filter…" shows only as a retry after a failure; both record it under `HKCU\Software\OmniControl`, and uninstall runs `netcfg -v -u nt_ndisrd` only with that record). With neither the network service nor administrator rights Network by app shows only `NetworkLimits.UnavailableLine` and, on an installed copy, "Install…" (a portable copy says the service needs the installed version): nothing is read (no per-program ETW session) or put into Windows. The driver is opened only while a limited program owns ports (port tables read every `ResourcesShaping.PortsIdle` while none does, every `.Ports` while one does, `Timing.ResourcesShaping`), every adapter tunnelled (new ones through the `resources.download-adapters` hardware watch), and only packets to the limited programs' ports (its filter table) reach OmniControl, so a new connection runs unlimited until the next look; IPv6 packets with extension headers pass unlimited; `NetworkLimits.Download` says what runs.
- Network service (threat note): a demand-start LocalSystem service (`OmniControlNetwork`, the app folder's `OmniControl.exe --network-service run <SID>`) that only Windows' service manager can run (started any other way it refuses). Its pipe `OmniControl.NetworkService` allows only the installing user's SID (read, write) and SYSTEM, denies NETWORK, is created first-instance-only (a squatted name makes the start fail), one client at a time; the user may only start, stop and query the service. Requests are a fixed, versioned list (`NetworkPipe`, unknown fields or names refused, 4 KB in, 512 KB out, 256 programs): a path must be a drive-letter `.exe` outside the Windows folder, without stream, wildcard or control characters, made whole, and exist for a Set or Block; limits 1 KB/s to 1 GB/s; nothing is run, opened or written by path, the path only names a firewall or QoS rule and a program to shape. Fail-open: everything leaves Windows when the client disconnects or the service stops, a crashed run's rules leave at the next start, and it stops itself after `Timing.NetworkServiceIdle`. The exe it runs cannot be swapped by its user: Setup installs for all users into Program Files, and `NetworkServiceSetup.Install` (also when Setup asks) refuses unless `CanServeFrom` reads from the access lists that only SYSTEM, administrators and TrustedInstaller own and may change the exe's folder, what it holds (inherited rights included) and every folder above it, so a portable or per-user copy never gets the service. What remains: the user it serves can block or limit any of their programs (Windows' own excepted) without an admin prompt.
- Install: Setup (administrator) puts OmniControl for all users into `Program Files\OmniControl`; settings stay per user in `%APPDATA%\OmniControl`, and the start-up entry, the Packet Filter record, the sign-in task's settings file and the service's user are those of the account Setup runs as (an administrator's own account when Setup is elevated with another account's password; the app's own "Install…" then puts the service on its user). Moving from the per-user install of 0.2.3 and earlier: Setup closes OmniControl, runs its old uninstaller silently with the Packet Filter record set aside (so the driver stays), deletes `%LOCALAPPDATA%\Programs\OmniControl` (only that usual folder), then installs and points the start-up entry, sign-in task and network service at the new exe; an unticked network service task removes a service left from before.
- Taskbar gadget placement (`Core/Engine/TaskbarSpot`, `Resources/Gadget/TaskbarGadget.Place`): only on the main taskbar (`Shell_TrayWnd`), never a second monitor's; Explorer's announcements (TaskbarCreated, its taskbar and light/dark setting changes) reach it only through `HardwareSignals` (`Taskbar`, `TaskbarSettings`), a new taskbar or scale gets a new window; a tray area that grows or shrinks (new icons, clock, language) is followed at the gadget's next read, not by an event; when Windows refuses the child window (owned instead) it does not slide with an auto-hidden taskbar. The tray icon is put back after an Explorer restart by Avalonia itself (it lets TaskbarCreated through to its own window).
- Gadget weather: Open-Meteo's rain chance is today's highest on the gadget (the hover tooltip can give the next hour's; sunrise, sunset and the next hours come in the same request); only Open-Meteo gives a next-hour rain chance, MET Norway gives no sunrise or sunset and OpenWeatherMap no next hours, so those tooltip lines are left out; MET Norway gives no feels-like or rain chance (high and low are the next 24 hours); OpenWeatherMap's free current weather gives no rain chance and its high and low are the current observation's range; "Use my location" needs Windows' location on for desktop apps. Places are sent rounded to two decimals.
- Rendering is Win32 only (`Program.cs`: `UseWin32().UseSkia()`) in Avalonia's default rendering order (ANGLE over Direct3D, then software; `av_libglesv2.dll` is shipped). Text is the system font (Segoe UI), no font is bundled.
- Trade-offs approved for idle cost: the USB pop-up and "device connected" rules follow Windows' device notice through the hardware watches (about `Timing.HardwareDebounce` after the plug); the laptop brightness check read runs for `Timing.OsdBrightnessCheckFor` only when Windows' brightness event is listened to; the autoscroll answer is renewed without a new lookup while the pointer rests; the OSD keep-warm redraw is every `Timing.OsdKeepWarm` (30 s).
- In a published build the .NET framework assemblies (except CoreLib) lose their precompiled ReadyToRun code (trimming rewrites them), so a little more JIT at start-up; putting it back costs about 19 MB installed.
