# OmniControl map

Where everything lives, the master pieces to reuse, how to add things, the allowed exceptions and the open items. Rules: `AGENTS.md`.
Keep it current in the same task: a new folder, master piece, recipe, exception or open item gets its line here (one line per folder, never per file).

## Layers (dependencies point down only)

```
OmniControl.App/Shell             start-up, main window, sidebar, search, footer; lists the feature modules
OmniControl.App/Features/<X>      one folder per feature: services, actions, states, pages, Timing.<X>.cs, its <X>Module.cs
OmniControl.App/Shared            what features share: Contracts, Ui (Controls, Pages kit, Restore, Styles), Services, Dialogs, Presets, Scripts
OmniControl.Core                  Windows access only (DDC/CI, Core Audio, WMI, WASAPI, VST hosting, hooks, Win32). No UI, no Avalonia, no settings files
```

- Core never references App; Shared should name no feature (some still do: open item); a feature reaches another only through a narrow interface or a `Func`/`Action` given by the shell (`IActionRegistry`/`IActionCatalogue`/`IActionRunner`, `IStateRegistry`/`IStateCatalogue`, `IOsd`, `IPresetGroups`, `IHardwareWatches`, `IPairedPcs`, `IPcBook`, `ActionGateSlot`, `PresetTriggersSlot`).
- A view-model never calls Win32/COM (it calls a service or Core); views hold layout and input wiring only.
- Start-up: `Program.cs` -> `App.axaml.cs` (theme `ThemeChoices`, surfaces, accent) -> `Shell/ShellViewModel` makes the shared registries and THE feature switch (`Features/FeatureSwitches`, which first takes a new Setup choice), then each module whose feature is on (`IFeatureModule.Features`, `Shell/ShellViewModel.Features.cs`) `Register`s through its own `FeatureScope` in start-up order (this order decides the master lists' order and the mouse hook's handler order), then each page in sidebar order registers its entries (`FeaturePage.Registers`, through its module's services) and its Restore defaults (`FeaturePage.Restore`, over the same services, kept on its `PageSlot`), then `PagesMade`. A page's view-model is made at its first use (opening, a search, "Show in OmniControl", a tab asked for; `Shell/PageSlot`) and kept for the run; the sidebar, search's page list, pickers' sections, preset manager and restore actions read only its static `PageInfo`. A page's actions, states and what they read belong to its module's services (Volume: `Volume/Pages/VolumeControls`; Displays: `Displays/Pages/DisplaysService`), made at the page's place in `FeaturePage.Registers`; an action only the page can do makes it through the module's one maker (`VolumeModule.Page`, the same instance the shell gets). `App.axaml` holds only the shared card rows' templates and the app-wide sizes.
- Shut-down: `Features/ShutdownSteps` runs every owner's steps in `ShutdownStage` order, each guarded; steps that put Windows back (displays, pointer, hook, effects) keep their stages; plug-in teardown is last.
- Saved files: `%APPDATA%\OmniControl`, one `DataStore` per file in `Shared/Services/DataStore.cs`, read and written only through `AppDataStore` (atomic). Every settings store saves with `AppDataStore.SaveSoon` (the text made once per burst, `Timing.SaveSoonDelay` after its last call, on the UI thread when it was saved there (else at once), written by a worker, so no disk on the UI thread; only a read, direct save or flush on another thread makes a waiting text there); only journals that must be on disk at once (display recovery, pointer and trackpad backups, swap trial, Windows OSD record, wake undo, engine journal, power journal, restore snapshots, an import's files) use `Save`/`SaveText`. A read, direct save or delete of a store writes or drops the waiting text first, and `FlushSaves` runs at shut-down (`ShutdownStage.Flush`), on an unhandled exception, before a backup or import, and after a restore. A damaged file is kept as `name.bad.json` and said once at start-up (`AppDataStore.TakeDamaged`). A restore from a backup or a wipe (`Backup/PendingRestore`) is staged and carried out at the next start, all or nothing: the whole replacement is worked out and checked (only backed-up stores, within `BackupFile.MaxBytes`), the new files and a copy of every file it changes are put on disk (`AppDataStore.WriteAtomically`, flushed) and the plan becomes their journal before any store changes; a start that finds the journal finishes it, or rolls it back when the kept files fail their SHA-256, and a write failing while it runs rolls it back at once; an area imported from another PC is written at once under the same journal (`PendingRestore.ApplyNow`, folder `pending-import`), rolled back when it does not read back or reload, and finished or rolled back at the next start. Logs: `AppDataStore.AppendLog` queues to the one background `LogWriter` (waiting lines within `Timing.LogQueueMaxBytes`, the oldest routine lines dropped past it with one "dropped" line, errors and hangs never; repeats written once with a count; roll-over at `Timing.LogMaxBytes` encoded bytes to `name.old.txt`; `FlushLogs` at exit and on an unhandled exception).
- Idle work: a view that wants fresh values holds a handle (`Shared/Services/HoldCount`): `MixerService.WatchClosely` (Audio and Volume page on screen, FX window, tray panel: 2 s scans, else `Timing.MixerRefreshIdle`), `MouseService.WatchPresses` (Mouse page), `SimulationSetup.WatchClosely` (Devices page: adb every `Timing.DeviceSimLive` also while a device has a simulation method, the emulators' memory only while on screen, the emulator search once then at each page open). Smart Devices' timed checks are automation rules (their timer is the rules' look), and Python is probed before the first automatic read only when a device uses Scripts. The autoscroll block's worker (`Core/Engine/Mouse/AutoscrollWatcher`) sleeps until the hook says the pointer moved (`MouseHook.PointerMoved`), rests after `CoreTiming.AutoscrollRestLooks`, and runs only while the block is on and the middle button is not mapped on every layer. The OSD's windows, keep-warm redraw and media watcher exist only while the OSD (and a media element) is on. Spinners animate only with the `.spinning` class, bound to the state that shows them. `ProcessPower.Compact` requests a background collection (never a forced blocking one); every explicit collection goes through `ShellViewModel.TryCompact`, skipped while sound runs through the process (`VolumeModule.StreamsAudio`, `ScreenshotModule.Records`). Fine 1 ms timers only through `Core/Engine/TimerResolution.Hold()` (recording, OSD on screen; meters need none). The mouse hook is installed only while a handler's owner says it needs it (`MouseHook.AddHandler(handler, needsHook)`, `Recheck` from `InputModule`); its last owner, `Input/Mouse/BackForwardGuard` (Back/Forward over OmniControl or the desktop), always does, so in practice it stays installed; the touchpad watcher only while `mouse.NeedsTrackpad || rules.NeedsTrackpad`. The main window's page area (`Shell/PageHost`) builds a page's view when it shows and lets it go the moment another page shows; `Shell/PageViewKeeper` says which stay (`ShellViewModel.KeptPages`): the open page only, or with App settings' "Keep recent pages ready" (`AppSettings.KeepRecentPages`, off by default) the open page, the last two visited and any other until it has been left as long as "Free memory after closing" says (Never: kept); a view is let go through `Shell/ViewLetGo` (tooltips, pop-ups and focus cleared, as for the whole window) and built again at their next opening (`ShellViewModel.ShownPage`; how far it was scrolled is kept in its view-model, `PageViewModel.Scroll`, and put back; a page stops its work in `OnOnScreenChanged(false)`); inside a page, a part shown by a switch (a card's other layouts, a group's body given as its `ContentTemplate`, a subgroup's cards, the Audio and Volume page's Easy and Advanced views and Mixer and Wiring tabs) is a `Pages/CardLayout`, built while shown and let go when hidden. `ProcessPower.Compact` gives memory back once the window has been hidden for `Timing.HiddenSettle` (also `Timing.CompactAfterStart`). After `Timing.UiReleaseAfterHidden` hidden (counted from the hide, never while minimised: `SetWindowShown(shown, hidden)`) the shell raises `ReleaseWindows`: `WindowLifecycle` closes the main window (made again by the next showing at its place, size and page, `MainWindow.Placement`; a start in the tray, `--background` or Start minimised, makes none until the first showing; the app ends only by its one exit path, `ShutdownMode.OnExplicitShutdown`) or, while a window it owns or the close question is open, gives the reason, which timing-log.txt gets, and the shell asks again after the same wait; the shell lets go of the hidden Actions and Hotkeys window (`SingleWindow.Release`), then `ProcessPower.CompactAfterRelease` (Skia's caches emptied, a background full collection requested, the large objects marked for compaction at the runtime's own next blocking collection; never a forced blocking one, which would stall the hook and the audio thread) `Timing.UiReleaseCompactAfter` later through the same guard, then `Timing.UiReleaseTrimAfter` later `ProcessPower.TrimWorkingSet` (`ShellViewModel.TrimAfterRelease`, on a worker, same sound guard, not when the window is back or the setting is Never; the only working-set trim, never on a timer of its own). Always instant (owner): the OSD, the mouse and keyboard hooks, the audio engine and the tray panel (`TrayService` builds it hidden after start-up and never lets it go). Page view-models, made at their first use, stay; a view that listens to its model does so only while attached (`ChoiceChip`'s pattern, also a control fed by a binding such as `LevelMeter.Model`), and no static holds a control (`RowEditing` marks the slider being adjusted with its `active` class), so a released window is never held. `UiTiming.Memory` writes the memory (Task Manager's figure too, `ProcessPower.PrivateWorkingSet`) and the visuals of the open windows to timing-log.txt `Timing.MemoryLineAfterStart` after start, at the hidden settle and after the release (with the visuals before it), and `Timing.UiReleaseLeakCheck` after the release whether the let-go main window was collected. The Resources poller (`ResourceMonitor.Need`) reads only the parts its needs ask for (`SampleParts`: page all, gadget its shown readings, rules the watched ones, adapters only while the adapter menu is open; each graphics adapter apart, `EachGpu`, only for readings that ask); sensor readings come from Windows' own sources (`Core/Engine/Resources/WindowsSensors`: GPU and disk load from performance counters, graphics temperatures from the graphics kernel, drive temperatures from the storage temperature query, ACPI thermal zones), each opened at its first need; LibreHardwareMonitor (`LibreSensors`, its assembly loaded only then) opens, with only the groups needed, for a reading Windows gives none of now, a chosen Hottest sensor of its own (only the group it was last found in) and the sensor menu while open (`SensorReader` decides); updated at most every `CoreTiming.SensorEvery`, temperatures every `CoreTiming.TemperatureEvery`, drives every `CoreTiming.StorageSensorEvery` while a disk reading is shown, else `CoreTiming.StorageTempEvery`.

## Recipes

- **Feature module:** `Features/<X>/<X>Module.cs` implementing `IFeatureModule`; in `Register(FeatureContext)` make services, register actions, states, watches, preset groups, `context.Imports.OnReload(store, ...)`, `context.Shutdown.Add(stage, what, step)`; offer `Pages` and `Templates`; add the module to the shell's start-up list (and the sidebar list if it has pages). A module the user may switch off declares its feature id: a `FeatureList` entry (name, description, `Live`), its id in `IFeatureModule.Features` (a module that holds several features reads `context.Features` at start and makes, registers and shows only the on features' parts, its page with the others' sections hidden and their search entries left out; `RunsWhenOff`: it runs with its features off too, with only its always-on parts and no pages, and restarts when one changes) and the same id as a component in `tools/setup.iss` (`FeatureIds` too). It registers only through its context (the `FeatureScope` takes back what is left when it is switched off), makes everything anew in `Register` (a live feature runs it again), gives back what the app keeps over a restart only in `context.Shutdown.AddWhenOff` steps, and whoever holds one of its services takes it as nullable (null while it is off).
- **View:** bindings are compiled (`AvaloniaUseCompiledBindingsByDefault`): every view, data template, and style or control theme whose setters bind names its `x:DataType`; a view's own properties through `RelativeSource={RelativeSource AncestorType=prefix:View}`, the parent's view-model through `$parent[ItemsControl].DataContext.X` (never a prefix inside a path).
- **Page:** `<Name>PageViewModel` (derives `PageViewModel` with its `public static readonly PageInfo Info` (title, icon, `NavGroup`, keywords, `RestoreKey`) passed to `base(Info)`; `SearchEntries` via `Entry`, `OnShown`, `OnOnScreenChanged`, `KeyHelp`) + `<Name>Page.axaml` in `Features/<X>/Pages`; one `FeaturePage(Info, make)` in the module's `Pages`, one `ViewTemplate.For<VM, View>()` in its `Templates` (never `App.axaml`). The view-model registers nothing: the page's actions, states, OSD elements and preset groups are registered by its module's services in `FeaturePage.Registers` (a page-only action, such as Other PCs' tab actions, forwards to the page when it exists). Tabs: override `Tabs` with a `PageTabs` shown by `PageTabsView`; anything opening the page at a tab calls `context.OpenPage(Title, tabName)`.
- **Page search words** (everything a user can read on a card is searchable: label, choices, menu items, tooltip, muted line): a page defines its search ONCE, as `protected override SearchBuilder SearchCards`, written as one `private static SearchBuilder Cards(owners?, MyPageViewModel? page)` that lists every card with its live editor (`.Add(card, page?._item)`, `.AddEach(list, card, editor)` for rows that come and go; no editor: words only) and is called with `page: null` by `public static Words(owners?) => Cards(owners, null).Words` (the `FeaturePage` word source) and with `this` by `SearchCards`; the base `SearchEntries` turns the cards that have an editor into results. Each card is a `SearchCard(Label, Keywords, Group, Title) { Choices, Menu, Tip, Note }` (a `static readonly` field of the page: `Choices` come from the list that fills the control, e.g. `CloseBehaviors.Labels`, `HardwareChecks.Labels`, `UiReleases.Labels`, `GroupsOpen.Labels`, `AccentService.Choices`, `TrayIconChoices.MenuWords`, `Enum.GetNames<T>()`; `Menu` the fixed rows of a menu, from shared constants; `Tip` and `Note` the tooltip and muted line) and THE page makes the item from it: `new ToggleItem(card, ...)`, `ChoiceItem(card, selected, apply)` (options = `card.Choices`), `GalleryItem(card, ...)`, `SliderItem`, `ButtonItem(card, buttonText, run)` (description = `card.Note`), `MenuChoiceItem`, `FactItem`, `FileItem`, `TextItem`, `ChoiceChipsItem`, `ScopeItem`, `AnchorItem`, so label, tooltip and choices are typed once; an item also reports what it shows now (`IEditorItem.SearchTexts`: options, menu rows, tooltip, note) and a new card type gets the same `(SearchCard, ...)` constructor. A card whose rows are live (devices, apps) gives its fixed words in its card and its live rows through its item's `SearchTexts`. A menu whose rows ask a service that may be slow (the paired PCs online now) is made `SearchesRows = false` on its `MenuChoiceItem`: its chip words and tooltip are searched, its rows are not. A card that lives in a list (a device, a paired PC, a program) is a result made by the page: a `FactItem` with an Open pill that selects it and opens the page (`DevicesPageViewModel.ResultFor`), or the row itself when it has a card template (`AutomationItem`, `AppNetItem`). Words that other pieces show come from where they are defined: a group's tips are consts of the page's `.Search.cs`; the Taskbar gadget tab's cards are one list (`GadgetSettingsModel.Cards`, each class owning its cards and making its items from them); `PresetGroup.Words` and `PresetManagerService.Words` (group names, apply and add words, switch, every preset's name; the manager's own search box finds a group by them too), `AppScopeModel.MenuWords`, `RestoreWords` (the shell adds it to every page that has Restore defaults), `TrayFlyoutModel.MenuWords`, `HotkeyAction.OptionWords` (an action's settings and their choices, for the Actions and Hotkeys window and the page index) and the Add effect window's effect settings and factory presets (`PluginLibrary.KeywordsOf`). `SearchIndex.Match`/`Similar` take an `accept` filter that acts before the cap (the category filter); `Similar` compares each distinct word of the list once per query (about 5 ms over 3,000 cards of 40 words, `SearchSpeedTests`). `tests/PageSearchWordsTests` is the guard: every page defines `SearchCards` (a page without results would be named, with a reason, in `NoResultsAllowed`, which is empty), `FeaturePage.NoResults` only for `NoResultsAllowed`, every card type has a card constructor, a page on the builder makes no card from a plain label (`new XItem("...", ...)`), every static card is in its page's words.
- **Action:** `context.Actions.Register(new HotkeyAction(id, title, Title, keywords, run) { ... })`; a level: `HotkeyAction.ForLevel` both directions; changing devices: one action with a device source + `RefreshDevices`; directions of one thing share a `Family`; a renamed id: `Move`; a standard Windows shortcut that does the same: `KeyEquivalent` (a built-in mouse action: `KeyEquivalent` on its `MouseActionCatalog` line).
- **State:** `context.States.Register(new StateEntry(...))`; call `Notify(id)` when it may have changed.
- **Hardware watch:** `context.Hardware.Register(new HardwareWatch(id, name, signals, refresh, looksStale))`; name it in the action's `HardwareWatch`.
- **OSD pop-up:** `context.Osd.Declare(name, icon)` once, then show through `IOsd`.
- **Preset group:** a provider deriving `Shared/Presets/PresetProvider` (the defaults said once; `ListPresetProvider<T>` for a `PresetList` after built-ins, entries worked out once per change) + `context.Presets.Register(new PresetGroup(id, section, title, provider))`; show it with `PresetPicker` on the group's header line.
- **Data store:** a `DataStore` line in `DataStores` (with `Import`/`MachineSpecific`/`NotImported`); the settings class loads and saves only through `AppDataStore`; reload on import via `context.Imports.OnReload`.
- **Setting slot:** a field in `AppSettings` read and written by the feature through `context.Settings.Slot(s => s.X, (s, v) => s.X = v)` (`ISettingSlot<T>`), never `AppSettings.Current`.
- **Timing:** a named value in `Features/<X>/Timing.<X>.cs` (`public static partial class Timing`, namespace `OmniControl.App.Shared.Services`, so calls stay `Timing.X`); Core values in `Core/CoreTiming.cs`.
- **Undo in a window:** its view-model owns an `UndoHistory`, calls `Record(name, undo, redo, mergeKey)` after each change (undo and redo through the same paths as the UI; recording during them is ignored) and `Clear()` when the window closes; the window's `Menu` gets `<c:EditMenu History="{Binding ...}" />`.
- **Restore defaults:** the module registers it on the page's entry (`FeaturePage.Restore`: an `IRestorable` over its services, usually `SettingsRestore`, never from the page view-model); a page that exists shows the result through its services' events or a small `ShowRestored`. The shell gives it the pill (right of the section title), its action and its share of Restore all (`Shell/ShellViewModel.Restore`). The copy taken first lives in `<key>-before-restore.json` and undo reads it from there (held in memory only when that save failed).
- **Style (cost per control):** every global style whose last part names a control type is tried, with its own watcher and setter objects, on every control of that type in every window, matching class or not; so a size or other fixed value is `{StaticResource}` (only theme, accent and surface brushes are `{DynamicResource}`), a piece of one window or control is styled in a file that window or control includes (not `App.axaml`), and a descendant selector names an ancestor by type or uses `>` rather than a class ancestor (`Grid.x TextBlock` is watched on every text in every grid). A control variant with more than one style is a ControlTheme (Button variants in `Styles/ButtonThemes.axaml` or the file of the piece, BasedOn `ButtonBase`, which every Button gets and which holds the master hover; Border and TextBlock variants without a BasedOn), picked by one `Type.x` style that sets `Theme`, so other controls try one style instead of all its own; the control keeps its class for its child selectors (a theme cannot hold one, they stay in the master files). Every selector in a theme names the class (`^.pill /template/ ...`, never a bare `^`): a class or state is what ranks a setter above the template's own bindings and Fluent's state styles. A theme ranks below every global style, so a theme's styles keep their old order, a variant whose looks lose to the hover states the hover last itself (pill, statetoggle, optioncard), and a global style may not set what a theme's state changes on the same part (the menu bar is hidden by its templates, not by `Border.menubar`; the drop-box chip's fill only while not hovered or focused). A common control (Slider, ScrollBar, TextBox, ComboBox...) has one theme BasedOn Fluent's, picked by a plain type style; a list kind styles its rows through its ListBox theme's `ItemContainerTheme`; a theme's selector may cross one `/template/` only (two crash the app at start, which a compile does not catch: run the Screenshots tool). Check a change to the master styles with the Screenshots tool's `--probe` and `--compare`, before and after, in both themes.
- **Apps scope:** store an `AppScopeSetting?`, make the model with `AppScopes.Group`/`.Card`, ask `AppScopeGate.Allows` before acting.

## Known limits (not bugs)

- Plug-ins load only from a local drive path (never a share or a mapped network drive), and while OmniControl runs as administrator only from folders only administrators can change (`PluginLoader`, one sentence otherwise); a plug-in's own DLLs are looked for only in its folder and System32 (`PluginLoader.LoadLibrary`, also for VST3 before NAudio loads it), so one that needs a DLL from PATH is refused. A restore from a backup leaves out effects' plug-in and impulse-response files and their states, as an import from another PC does (`DataStore.NotImportedInside`). Equalizer APO's config files are written only when neither they nor the folder is a link (`Core/Engine/PlainFile`; each write opens the file itself, never a link's target, and checks that same handle, `PlainFile.OpenToWrite`).
- Effects an engine does not run (`FxKind.Engines`) are stored only and the UI says so; VST3 plug-ins on Equalizer APO rows are kept, not run; a blend's dry part is not delayed to match a plug-in's latency.
- Pan needs Windows to allow per-channel session levels (`AudioSession.CanPan`); per-app output uses an undocumented interface (`CoreAudio.Routing.cs`); hiding Windows' OSD is best-effort (`WindowsOsd`).
- The mouse hook cannot act on programs running as administrator unless OmniControl runs as administrator; it never runs on the secure desktop (UAC prompt, Ctrl+Alt+Del, lock screen), never sees a mouse passed straight into a virtual machine (USB pass-through), and a program that reads the device below Windows' input (some anti-cheat drivers) still gets the original button. Another program's low-level mouse hook installed later (XMouseButtonControl) is asked first and may take a button before OmniControl sees it.
- Actions sent to a remote-input window as keys: only mouse buttons, middle-click and trackpad gestures (wheel gestures act on this PC's screen areas, custom rules decide their own steps, keyboard hotkeys already reach the remote when it has the keyboard); keys go into a remote window one event at a time, `CoreTiming.RemoteKeyGapMs` apart, by scan code (a shortcut of four keys takes about 45 ms); where Remote Desktop keeps shortcuts on this PC (keyboardhook 0, or 2 while not full screen: no title bar and covering its monitor, `WindowQuery.CoversItsMonitor`) Alt+Tab and the like go as its own replacements, while Windows-key shortcuts have none and act on this PC (the mouse log says so once per run); the keyboardhook is read from the .rdp file named on mstsc's command line, else Documents\Default.rdp, else Windows' default 2, so a session started another way may be judged wrongly; Windows App / msrdc has no swaps (its setting is not in a file); keys held while a button is held and wheel-gesture keys are sent as before (all at once); the remote's volume keys move by its own step, not the action's.
- Other PCs is basic only (LAN or Tailscale/ZeroTier address); no relay; Windows Remote Desktop covers more. Pairing and the link (protocol `PcProtocol.Version` 3) need the same version on both PCs; an older PC is refused with one sentence when pairing, and paired PCs on different versions just show offline.
- While OmniControl runs as administrator, a web or Settings address (`WebPage.Open`, the one way every link opens, off the UI thread, a failure reported through the caller's `report`) goes through Explorer's own ShellExecute (`Core/Engine/ShellDesktop`, on a short STA thread with `CoreTiming.ShellOpenWait`); anything else it opens through the shell (`NormalRights.Open`), and an address Explorer could not take, is handed to a short-lived normal-rights copy of itself, so a file or address Windows then fails to open is not reported; with Explorer not running, or Windows' Secondary Logon service off (it starts a program with another token), nothing is started and one sentence says so.
- Equalizer APO is its own program: OmniControl ships its official 1.4.2 x64 installer unmodified (`third_party/equalizer-apo`, about 12 MB, copied to the app folder's `equalizer-apo\`; `ApoInstaller` checks its pinned SHA-256 and holds it open while it runs) and uses Equalizer APO's own installer, Device Selector, uninstaller and Installed apps entry as they are. Setup's task "Equalizer APO", on by default, runs it with NSIS `/S` after the files unless it is installed (its Uninstall entry, or its InstallPath holding EqualizerAPO.dll); `/S` skips its pages (its default folder, its update checker ticked) but still opens its Device Selector (`/i`) and waits for it, then its device check and a "can be reopened from the Start menu" note; when that check fails its installer only sets NSIS's reboot flag, which a silent install never acts on, so Setup's finish page and the app's result say to restart Windows if the check showed a device that didn't start. The app's "Install Equalizer APO…" (Portable too) runs the same file the same way (one administrator prompt) and the first use of a master effect only offers it, once per run, after the user changed the master's effects or the routing; "Equalizer APO devices…" opens its Device Selector. OmniControl reads, never writes, its registration and which devices have it in their FxProperties, and writes only its own chain into the config folder Equalizer APO's ConfigPath names; whether it really started on a device is Device Selector's check, which OmniControl does not run. OmniControl's uninstall offers to remove Equalizer APO only when Setup's receipt says Setup installed it; one installed before, by hand or by the app's "Install Equalizer APO…" (which writes no receipt) stays.
- Download limits (`Core/Engine/Resources/DownloadShaper`) need Windows Packet Filter (`ndisrd.sys` and its `ndisrd` service; its official Windows 10+ x64 driver files, taken unmodified from its MSI, ship in `third_party/windows-packet-filter/driver`, copied to the app folder's `windows-packet-filter\` by the App csproj; Setup's task "Install Windows Packet Filter", on by default, runs Windows' `netcfg -v -l <inf> -c s -i nt_ndisrd` after the files unless the driver is there, a failure only shows one line; while OmniControl runs as administrator the first download limit set, or a saved one at start-up, installs it the same way (hidden, no prompt; one prompt with the network service) after checking the files' pinned SHA-256 in `PacketFilterSetup`, and "Install Windows Packet Filter…" shows only as a retry after a failure; both write the receipt `HKLM\SOFTWARE\OmniControl` `PacketFilterInstalled` in the same elevated step (the app's through Windows' PowerShell, which runs netcfg and then records it), and uninstall runs `netcfg -v -u nt_ndisrd` only with that receipt). With neither the network service nor administrator rights Network Traffic Control shows only `NetworkLimits.UnavailableLine` and, on an installed copy, "Install…" (a portable copy says the service needs the installed version): nothing is read (no per-program ETW session) or put into Windows. The driver is opened only while a limited program owns ports (port tables read every `Shaping.PortsIdle` while none does, every `.Ports` while one does, and at once for a packet to an unknown port at most every `.Miss`, `CoreTiming.Shaping`), every Ethernet-style adapter tunnelled, never an IP-medium WinTun tunnel (Tailscale, WireGuard: its frames cannot be shaped and its traffic could be lost, so limits do not apply there) (new ones through the `resources.download-adapters` hardware watch), and meanwhile every received TCP and UDP packet (its filter table) reaches OmniControl, so a new connection is limited from its first packet; IPv6 packets with extension headers pass unlimited; `NetworkLimits.Download` says what runs. The Resources page's "Packet filter" switch (on the Network Traffic Control group's header, left of its Adapter choice; `ResourcesSettings.PacketFilterOn`, not in presets; the group's Restore defaults turns it on) is for conflicts with other software: off, the shaper never opens the driver (download limits kept, shown as "Packet filter is off"; upload limits and blocks unaffected) and `PacketFilterSetup.Attach` detaches its binding from every adapter (Windows' own `Disable-NetAdapterBinding`, hidden ones too, through the elevated helper, read back over WMI); on attaches all again. A refused prompt or failure turns the switch back with one sentence. While off and OmniControl is administrator, start-up and the `resources.download-adapters` watch detach it from adapters Windows added (no prompt); without administrator a new adapter keeps its binding (unused) until the switch is changed.
- Network Traffic Control is its own module and page but keeps its rules in resources.json, so a Resources preset still holds and applies its rules and pins (`ResourcesSetup.Apps`, `Scoped`, `Pinned`) beside its own presets (`TrafficPresets`, rules only), its programs are read at the Resources page's "Read every", and both modules register the one resources.json reload (switching one off takes the reload away until the next start): a store of its own (with a move of the rules out of the presets) would part them.
- Network service (threat note): a demand-start LocalSystem service (`OmniControlNetwork`, the app folder's `OmniControl.exe --network-service run <SID>`) that only Windows' service manager can run (started any other way it refuses). Its pipe `OmniControl.NetworkService` allows only the installing user's SID (read, write) and SYSTEM, denies NETWORK, is created first-instance-only (a squatted name makes the start fail), and OmniControl talks on it only after checking the process at its other end is the running service (`NetworkServiceSetup.ServerProblem`: the pipe's server process id against the service's, else one line and nothing sent), one client at a time; the user may only start, stop and query the service. Requests are a fixed, versioned list (`NetworkPipe`, unknown fields or names refused, 4 KB in, 512 KB out, 256 rules; a rule's place is an adapter id with a plain name, or a network category for an upload limit): a path must be a drive-letter `.exe` outside the Windows folder, without stream, wildcard or control characters, made whole, and exist for a Set or Block; limits 1 KB/s to 1 GB/s; nothing is run, opened or written by path, the path only names a firewall or QoS rule and a program to shape. Fail-open: everything leaves Windows when the client disconnects or the service stops, a crashed run's rules leave at the next start, and it stops itself after `Timing.NetworkServiceIdle`. The exe it runs cannot be swapped by its user: Setup installs for all users into Program Files, and `NetworkServiceSetup.Install` (also when Setup asks) refuses unless `CanServeFrom` reads from the access lists that only SYSTEM, administrators and TrustedInstaller own and may change the exe, its folder, what it holds (inherited rights included, and for the service and the sign-in task every file and folder under it, each with its own list: `wholeFolder`) and every folder above it, so a portable or per-user copy never gets the service. What remains: the user it serves can block or limit any of their programs (Windows' own excepted) without an admin prompt.
- Install: Setup (administrator) puts OmniControl for all users into `Program Files\OmniControl`; settings stay per user in `%APPDATA%\OmniControl`, the receipts of what Setup installed (`HKLM\SOFTWARE\OmniControl`) are the machine's, the sign-in task is for the user signed in to the session, ticked by that user's own "Run as administrator" and used only while it is on (a silent Setup without the tick keeps one from before only when it is exactly Setup's), and the start-up entry and the service's user are those of the account Setup runs as (an administrator's own account when Setup is elevated with another account's password; the app's own "Install…" then puts the service on its user). Setup's Tailscale firewall rule is added only with Other PCs and while Tailscale's service is installed (else the Other PCs Tailscale checklist's "Allow" adds it); uninstall removes it either way. Setup's "Choose features" page (Inno's components page: types Everything, Sound only, Monitoring only, Custom) installs every file whatever is ticked; the Equalizer APO task shows only with Sound and effects, the Packet Filter and network service tasks only with Network Traffic Control; it writes `FeaturesOff` beside the receipts (a silent Setup only when `/COMPONENTS` or `/TYPE` is given), which the app takes once into settings.json; uninstall removes it. Setup never starts cmd or an OmniControl.exe from a user-writable folder while elevated: it sets the running copy's quit event (`SingleInstance`) itself and finds running copies and the service's state with `tasklist.exe` and `sc.exe` from System32. Moving from the per-user install of 0.2.3 and earlier: Setup closes OmniControl, runs its old uninstaller silently with the token of the person who started Setup (never elevated) and the Packet Filter record set aside (so the driver stays), deletes `%LOCALAPPDATA%\Programs\OmniControl` (only that usual folder), then installs and points the start-up entry, the sign-in task (when ticked) and network service at the new exe; an unticked network service task removes a service left from before.
- Taskbar gadget placement (`Core/Engine/TaskbarSpot`, `Resources/Gadget/TaskbarGadget.Place`): only on the main taskbar (`Shell_TrayWnd`), never a second monitor's; Explorer's announcements (TaskbarCreated, its taskbar and light/dark setting changes) reach it only through `HardwareSignals` (`Taskbar`, `TaskbarSettings`), a new taskbar or scale gets a new window; the window is layered and shows only the picture `TaskbarSpot.Paint` gives it (the window drawn by `GadgetWindow.DrawInto` after each placement and hover-edge change), since a software-drawn child paints into the taskbar's own surface, which Windows 11's XAML taskbar covers; a tray area that grows or shrinks (new icons, clock, language) is followed at the gadget's next read, not by an event; when Windows refuses the child window (owned instead) it does not slide with an auto-hidden taskbar. Position Left (`TaskbarButtons.RunEnd`): the end of the run of the taskbar's own controls that starts at its left (top) end, read through UI Automation (Windows 11's Start, Widgets and program buttons are XAML, without windows of their own): with centred icons that is the Widgets button (or the taskbar's edge when it is hidden), with left-aligned icons the last pinned or running program; controls more than 24 px (at 100 %) apart end the run, controls wider than a third of the taskbar count as containers and are left out. It is looked at again only when the gadget places itself, at most every `Timing.ResourcesGadgetLeftLook` (and at once after a taskbar announcement or a change of position), so a program button that appears can sit under the gadget for up to that long; until the first look (and if UI Automation cannot read the taskbar) the gadget sits on the right. When the left run reaches the tray (many program buttons) the gadget is kept inside the taskbar and overlaps the buttons; a third-party taskbar (ExplorerPatcher, StartAllBack) or another layout of Windows' own may put other controls there. Space to the tray is also the space after the left buttons on Left. The tray icon is put back after an Explorer restart by Avalonia itself (it lets TaskbarCreated through to its own window).
- Sensors (RAM plan 2): readings come from Windows first, so they read as Task Manager does: GPU usage is the busiest graphics engine summed over programs (was the driver's "GPU Core" load); "CPU temperature" on Auto is the sensor library's CPU package (`TemperaturePick`: package or Tdie, then Tctl, then cores and CCDs), so the library's CPU group stays loaded while it is shown; the hottest ACPI thermal zone only when the library reads no CPU sensor (no PawnIO driver; then it is not asked again until the sources close, `Timing.ResourcesIdleClose` after no sensor reading is wanted); graphics and drive temperatures are what the driver reports to Windows (one value per adapter, whatever the driver calls its temperature; a drive or card that reports none falls back to the sensor library's core, then hot spot, memory and regulator sensors last, and a drive the library cannot read either stops asking it until a disk change); the Hottest sensor on Auto is the hottest of Windows' sensors, of the library's groups open for other readings, and of the library's only for a group Windows has none in; a Hottest sensor chosen before this change keeps the library's id and opens the library's group as before. Every temperature reading (each disk's too) can be set to any one sensor (`SensorMenu`); a chosen one that is gone reads as Auto.
- Gadget weather: Open-Meteo's rain chance is today's highest on the gadget (the hover tooltip can give the next hour's; sunrise, sunset and the next hours come in the same request); only Open-Meteo gives a next-hour rain chance, MET Norway gives no sunrise or sunset and OpenWeatherMap no next hours, so those tooltip lines are left out; MET Norway gives no feels-like or rain chance (high and low are the next 24 hours); OpenWeatherMap's free current weather gives no rain chance and its high and low are the current observation's range; "Use my location" needs Windows' location on for desktop apps. Places are sent rounded to two decimals.
- Rendering is Win32 only and in software by default (`Program.cs`: `UseWin32().UseSkia()`, `Win32RenderingMode.Software`): no ANGLE, Direct3D or GPU driver in the process; App settings' "Use GPU drawing" (`AppSettings.GpuDrawing`, off, read by `Program.Main` before Avalonia starts, so from the next start) gives Avalonia's own order `AngleEgl` then `Software` (`av_libglesv2.dll`, 5.2 MB, is shipped for it and loaded only then); transparent windows (OSD, tray panel, overlays) use Avalonia's redirection-bitmap path (Windows' blur-behind with an empty region), no Mica or acrylic; every frame is drawn by the CPU, so a large window on a 4K screen costs more CPU while it animates or scrolls. Text is the system font (Segoe UI), no font is bundled. Skia's image and blur-mask cache is held to 8 MB (`ProcessPower.LimitDrawingCaches`, its default 32 MB; Avalonia's `SkiaOptions` sizes only a GPU cache, unused here).
- Trade-offs approved for idle cost: the USB pop-up and "device connected" rules follow Windows' device notice through the hardware watches (about `Timing.HardwareDebounce` after the plug); Windows' brightness event is listened to (`Core/Engine/BrightnessWatcher`, only while the OSD shows brightness) only after a first read found a laptop panel, and the check read then runs for `Timing.OsdBrightnessCheckFor`; the autoscroll answer is renewed without a new lookup while the pointer rests; the OSD keep-warm redraw is every `Timing.OsdKeepWarm` (30 s).
- In a published build the .NET framework assemblies (except CoreLib) lose their precompiled ReadyToRun code (trimming rewrites them), so a little more JIT at start-up; putting it back costs about 19 MB installed. Only the app (`OmniControl.dll`) and `Avalonia.Base` are precompiled (csproj `ReadyToRunOnly`): 4.8 MB more in the Setup, 13.8 MB installed; adding `Avalonia.Controls` would pass the owner's 5 MB limit (5.4 MB). `LibreHardwareMonitorLib` is precompiled too, past that limit by the owner's choice (1.2 MB to 2.5 MB installed, about 0.5 MB more compressed), so its sensors open with less JIT.
