# OmniControl code map

Read this first. It says where each concern lives, so a change or a bug can be found without reading everything.
Keep it current: when you add or move a file, update the matching line.
Shared behaviours (slider wheel and reset, number typing, live apply, centring, density) are described in the "Global design principles" of `AGENTS.md`; they live in `Pages/ValueWheel.cs` (`StepOf` = how far one notch moves a range (1 % of it, at least 1: `Core/Models/Percent.StepOf`, the one step rule), also used by the EQ graph's points; sliders and knobs), `Pages/SliderReset.cs` (any `RangeBase`: sliders and knobs; each slider's default comes from its model where one exists (`VolumeRow.VolumeReset` / `PanReset` for the Mixer's knobs): `SliderItem.ResetValue`, `EqBandItem.Default*` from `Eq.DefaultFor`, `FxSlotViewModel.DefaultWet`), `Pages/NumberText.cs` (a slider's value text that can be typed: double-click it or Ctrl+Enter on the slider (the first value text in the slider's own row grid); whole numbers unless `Decimals` is set; used by `SliderRow`, the Easy rows, the knobs (`OpensOnDoubleClick` off: a knob's single click opens it through `Knob.TypeRequestedEvent`, answered once by `NumberText.Register()` at start-up) and the equaliser's Hz, dB, octaves and Q), `Pages/ComboKeys.cs` (keyboard of every drop-down, a class handler on `TopLevel` registered at start-up: closed Alt+Down/F4/Space/Enter open it; open Up/Down wrap, Home/End, Enter/Space pick, Esc close, letters jump; rules in the pure `Decide`/`FindByPrefix`, tested in `ComboKeysTests`; Left/Right on a lone drop-down card step it via `ComboKeys.Step`, as the wheel does), `Controls/Knob.cs` + `KnobFace.cs` + `KnobMath.cs` (the master knob: 270 degree sweep, pan from the centre, drag up/down, one click types, double-click resets, keys; the pure maths in `KnobMath`, tested in `KnobMathTests`; template and colours `Styles/Knobs.axaml`, sizes `Knob*` in App.axaml), `Pages/RowEditing.cs` (keys inside a card list, including a knob's (Enter starts turning it with its own keys, Enter/Esc end, Home resets, Ctrl+Enter types) and every vertical slider's keys: Up/Down a step, Shift or PageUp/PageDown a large step, Ctrl one tick, Home or 0 its reset value, Esc back to the card), `Pages/TypedNumber.cs` (the one rule for reading a typed number, whole or with decimals, also used by the master picker's settings page `Picker/PickerMenu.axaml.cs` / `OptionItem`), `Styles/Theme.axaml` (incl. `TextBlock.hint` for a grey caption that carries state, never keyboard instructions, and the `BrushOn` / `BrushOnHover` green) and `App.axaml`, and every control must use them rather than its own copy. Wrap-around list stepping is `Services/Wrap.cs`; the 0-100 percent range (and the 0-200 `BoostMax` of a combined microphone member's level) is `Core/Models/Percent.cs` (`OfRange` = a value's 0-100 share of its range, what a level pop-up draws).

## Layers (dependencies point down only)

```
OmniControl.App/Pages, Shell      views + view-models (what the user sees and does)
OmniControl.App/Osd, Audio,       app services (state, timers, persistence, OSD, mixer)
  Hotkeys, Services
OmniControl.Core                  Windows access only (DDC/CI, Core Audio, WMI, NAudio WASAPI, VST3 (NAudio) and VST2 hosting, APO registry). No UI, no Avalonia, no settings files.
native/EqualizerAPO               C++ APO, optional fork (separate build, loaded by Windows, configured through config.txt)
```

- Core never references App. Services never reference Pages. Pages reference services, never each other. Exception: `App/Fx` (the FX windows) is a feature module and reuses the shared card types from `Pages/`; nothing in `Pages` depends on it except through `FxWindowService` (`Open(key)`, `AskAsync`).
- A view-model never calls Win32 or COM directly: it calls a service or Core.
- Views (`.axaml`) hold layout only; logic goes in the view-model or a service. Code-behind is for wiring input events.

**To add a new action:** in the page's constructor, `hotkeys.Register(new HotkeyAction(id, title, Title, keywords, run, ...))` (pass `group:` for Hardware/Software, a device source for variable devices). For an up/down level use `HotkeyAction.ForLevel(..., new HotkeyLevel(levelId, name), +1 / -1, step)` for the two directions; the wheel gestures then offer it. If it shows something in the OSD, `osd.Declare(name)` once in the same constructor. Nothing else: the Shortcuts page, search, the mouse and gesture pickers and the OSD switches pick it up.
For things that come and go (a monitor), register ONE action per control with a device source (`deviceNoun` + `Func<IReadOnlyList<HotkeyDevice>>`) and call `RefreshDevices` on it when the devices change; never register an action per device. The action carries the user's scope (all, or picked devices, `UseSelected` / `DeviceIds`) and a gesture on its level drives the same scope. A level id is stored by gestures.json and must not contain `:` (stored actions are split at the first colon) or clash with another page's (the Volume page owns `volume`). The Displays page does this for every control, from the descriptors in `Pages/Displays/DisplayControls.cs`.

## Rules that keep it separated

1. One concern per file, and no file over 700 lines. Split by concern (a `partial` class is fine) before it grows past that.
2. Settings files: one class owns one json file (`AppSettings`, `OsdSettings`, `MixerSettings`, `hotkeys.json` via the registry).
3. Search lists any `IEditorItem` with a template in `App.axaml`. Do not teach search about concrete card types. Pages build their entries with `PageViewModel.Entry`, never with a typed category.
   The results list is `ListBox.results` in `MainWindow.axaml`: title column `*` (wraps, up to 3 lines), editors in one shared right-hand `Auto` column (`SearchEditor`, least width `SearchEditorMinWidth` in `App.axaml`). Search-only placement of the centred editors (combo, gallery, toggle, hotkey box hug the right) is in `Theme.axaml` under `ListBox.results`; their page placement lives in `Theme.axaml` too (`ComboBox.choice`, `GalleryRow Border.gallery`), not on the controls.
4. A new feature page adds hotkeys through `HotkeyRegistry` (see AGENTS.md rule 4 and "Master lists" above), with its own `Title` as the category.
5. Behaviour that depends on a Windows quirk gets a comment saying which quirk, next to the code that works around it.

## Known limits (not bugs to chase)

- The engine runs the three equalisers (Parametric, 32 Bands, 16 Bands), Gain, Compressor, Limiter and VST3 and VST2 plug-ins for programs, and the equalisers, Gain, IR Loader and VST2 plug-ins in the master APO; Delay, Noise gate, Reverb (and IR Loader for programs) are stored only (`FxKind.Engines`). Recording-device chains and combined-microphone chains run through a cable. VST3 and VST2 plug-ins run inside OmniControl's process (a native crash or hang in a plug-in takes the app down; the journal restores sound at the next start; a hang while unloading at exit is cut short by `ExitGuard`). Equalizer APO runs a VST2 on the master or on a program's cable inside Windows' audio engine (audiodg.exe), from the settings saved in OmniControl, without a window; VST2 is a discontinued format (Steinberg no longer licenses its SDK), hosted for plug-ins users already own. Only the first effect class of a .vst3 file is used; mono and stereo main buses only (side-chain and extra buses stay inactive); NAudio.Vst3 runs plug-ins in its "offline" process mode; a plug-in's settings list drives its parameters through NAudio.Vst3's controller and IParameterChanges path; it was not tried with real plug-ins (HANDOVER, "FX editors for small screens"). The built-in effect parameter lists follow TabForge (MIT, same author).
- Pan relies on Windows allowing per-channel levels for a program's session; if it doesn't, the pan slider has no effect (`AudioSession.CanPan`).
- Per-app output device uses an undocumented Windows interface (`CoreAudio.Routing.cs`), unverified against a reference. Measured on build 26300 (read side only): it answers 0x80070057 for a process id that is not running.
- Hiding Windows' own OSD is best-effort (`WindowsOsd.cs`; diagnostics in `%APPDATA%\OmniControl\osd-log.txt`).
