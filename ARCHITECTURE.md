# OmniControl code map

Read this first. It says where each concern lives, so a change or a bug can be found without reading everything.
Keep it current: when you add or move a file, update the matching line.
Shared behaviours (slider wheel and reset, number typing, live apply, centring, density) are described in the "Global design principles" of `AGENTS.md`; they live in `Pages/ValueWheel.cs` (`StepOf` = how far one notch moves a range, also used by the EQ graph's points), `Pages/SliderReset.cs` (each slider's default comes from its model where one exists: `SliderItem.ResetValue`, `EqBandItem.Default*` from `Eq.DefaultFor`, `FxSlotViewModel.DefaultWet`), `Pages/NumberText.cs` (a slider's value text that can be typed: double-click it or Ctrl+Enter on the slider (the first value text in the slider's own row grid); whole numbers unless `Decimals` is set; used by `SliderRow`, the Volume rows and the equaliser's Hz, dB, octaves and Q), `Pages/RowEditing.cs` (keys inside a card list, including every vertical slider's keys: Up/Down a step, Shift or PageUp/PageDown a large step, Ctrl one tick, Home or 0 its reset value, Esc back to the card), `Pages/TypedNumber.cs` (the one rule for reading a typed number, whole or with decimals, also used by the master picker's settings page `Picker/PickerMenu.axaml.cs` / `OptionItem`), `Styles/Theme.axaml` (incl. `TextBlock.hint` for the grey help paragraph and the `BrushOn` / `BrushOnHover` green) and `App.axaml`, and every control must use them rather than its own copy. Wrap-around list stepping is `Services/Wrap.cs`; the 0-100 percent range is `Core/Models/Percent.cs` (`OfRange` = a value's 0-100 share of its range, what a level pop-up draws).

## Layers (dependencies point down only)

```
OmniControl.App/Pages, Shell      views + view-models (what the user sees and does)
OmniControl.App/Osd, Audio,       app services (state, timers, persistence, OSD, mixer)
  Hotkeys, Services
OmniControl.Core                  Windows access only (DDC/CI, Core Audio, WMI, NAudio WASAPI, VST3 (NAudio) and VST2 hosting, APO registry). No UI, no Avalonia, no settings files.
native/EqualizerAPO               C++ APO, optional fork (separate build, loaded by Windows, configured through config.txt)
```

- Core never references App. Services never reference Pages. Pages reference services, never each other. Exception: `App/Fx` (the FX windows) is a feature module and reuses the shared card types from `Pages/`; nothing in `Pages` depends on it except through `FxWindowService` (`Open(key)`, `AskAsync`).
- A view-model never calls Win32 or COM directly: it calls a service or Core.
- Views (`.axaml`) hold layout only; logic goes in the view-model or a service. Code-behind is for wiring input events.

**To add a new action:** in the page's constructor, `hotkeys.Register(new HotkeyAction(id, title, Title, keywords, run, ...))` (pass `group:` for Hardware/Software, a device source for variable devices). For an up/down level use `HotkeyAction.ForLevel(..., new HotkeyLevel(levelId, name), +1 / -1, step)` for the two directions; the wheel gestures then offer it. If it shows something in the OSD, `osd.Declare(name)` once in the same constructor. Nothing else: the Shortcuts page, search, the mouse and gesture pickers and the OSD switches pick it up.
For things that come and go (a monitor), register ONE action per control with a device source (`deviceNoun` + `Func<IReadOnlyList<HotkeyDevice>>`) and call `RefreshDevices` on it when the devices change; never register an action per device. The action carries the user's scope (all, or picked devices, `UseSelected` / `DeviceIds`) and a gesture on its level drives the same scope. A level id is stored by gestures.json and must not contain `:` (stored actions are split at the first colon) or clash with another page's (the Volume page owns `volume`). The Displays page does this for every control, from the descriptors in `Pages/Displays/DisplayControls.cs`.

## Rules that keep it separated

1. One concern per file, and no file over 700 lines. Split by concern (a `partial` class is fine) before it grows past that.
2. Settings files: one class owns one json file (`AppSettings`, `OsdSettings`, `MixerSettings`, `hotkeys.json` via the registry).
3. Search lists any `IEditorItem` with a template in `App.axaml`. Do not teach search about concrete card types. Pages build their entries with `PageViewModel.Entry`, never with a typed category.
   The results list is `ListBox.results` in `MainWindow.axaml`: title column `*` (wraps, up to 3 lines), editors in one shared right-hand `Auto` column (`SearchEditor`, least width `SearchEditorMinWidth` in `App.axaml`). Search-only placement of the centred editors (combo, gallery, toggle, hotkey box hug the right) is in `Theme.axaml` under `ListBox.results`; their page placement lives in `Theme.axaml` too (`ComboBox.choice`, `GalleryRow Border.gallery`), not on the controls.
4. A new feature page adds hotkeys through `HotkeyRegistry` (see AGENTS.md rule 4 and "Master lists" above), with its own `Title` as the category.
5. Behaviour that depends on a Windows quirk gets a comment saying which quirk, next to the code that works around it.

## Known limits (not bugs to chase)

- The engine runs the three equalisers (Parametric, 32 Bands, 16 Bands), Gain and VST3 and VST2 plug-ins for programs, and the equalisers, Gain, IR Loader and VST2 plug-ins in the master APO; Compressor, Limiter, Delay, Noise gate, Reverb (and IR Loader for programs) are stored only (`FxKind.Engines`). Recording-device chains run in Equalizer APO in Fast mode (only on a microphone it is on; VST2 run there, VST3 saved only there) and through a cable in Full control; combined-microphone chains run only in Full control. VST3 and VST2 plug-ins run inside OmniControl's process (a native crash or hang in a plug-in takes the app down; the journal restores sound at the next start; a hang while unloading at exit is cut short by `ExitGuard`). In Fast mode Equalizer APO runs a VST2 on the master or a microphone inside Windows' audio engine (audiodg.exe), from the settings saved in OmniControl, without a window; VST2 is a discontinued format (Steinberg no longer licenses its SDK), hosted for plug-ins users already own. Only the first effect class of a .vst3 file is used; mono and stereo main buses only (side-chain and extra buses stay inactive); NAudio.Vst3 runs plug-ins in its "offline" process mode; a plug-in's settings list drives its parameters through NAudio.Vst3's controller and IParameterChanges path; it was not tried with real plug-ins (HANDOVER, "FX editors for small screens"). The built-in effect parameter lists follow TabForge (MIT, same author).
- Pan relies on Windows allowing per-channel levels for a program's session; if it doesn't, the pan slider has no effect (`AudioSession.CanPan`).
- Per-app output device uses an undocumented Windows interface (`CoreAudio.Routing.cs`), unverified against a reference.
- Hiding Windows' own OSD is best-effort (`WindowsOsd.cs`; diagnostics in `%APPDATA%\OmniControl\osd-log.txt`).
